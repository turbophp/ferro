## 0. How to read this document

- **MUST / SHOULD / MAY** are normative (RFC 2119 sense).
- §21 is the **decision log**. Decisions there are settled — do not re-litigate them in code review or refactors. Open items carry an interim default so nothing blocks implementation.
- Build in milestone order (§17). M0 has an explicit task order (§17.1); start there.
- The machine-readable protocol registry in `/proto` (§20.2) is the single source of truth for method ids, flags, error codes, and type tags. Both the Rust and PHP codecs generate constants from it. Any protocol change MUST update the registry, the golden vectors, and both codecs in the same change set.
- Where this spec is silent, prefer: correctness over throughput, explicit configuration over inference, and the smallest surface that turns the acceptance suites green.

## 1. Problem statement

PHP-FPM is shared-nothing: every worker owns its own database connections, prepared-statement caches, and TLS sessions. 200 workers means 200 upstream connections and zero cross-worker reuse. PDO, designed in 2004, compounds this: synchronous only, stringly typed, connection-oriented, and inconsistent across drivers.

Ferro is **not a database**. It is a per-host access engine: one Rust daemon that owns all upstream connections, pools them in transaction mode, multiplexes many PHP workers over a local socket, and exposes a modern typed API — while remaining a drop-in replacement for Doctrine DBAL and Laravel Eloquent so existing applications adopt it by changing configuration only.

**Prior art and positioning.** PgBouncer proves host-level transaction pooling and shares the session-state detection limits that §7.4 confronts explicitly. Prisma ran a Rust query engine out-of-process and later retreated in-process for operational reasons — but Prisma's engine served a single Node client and had no cross-process pooling upside; Ferro's entire point is N workers sharing one daemon, which is exactly the case where out-of-process pays. sqlx supplies the model for §11's compile-time checked queries. ProxySQL/RDS Proxy demonstrate the ops value of a protocol-aware middle tier; Ferro differs by owning **both** ends of the wire (client library and daemon), which is what makes tx-id pinning, typed hydration, and the manifest handshake possible.

## 2. Goals

1. **G1 — Pooling:** N workers share M real connections (M ≪ N) with transaction-mode pooling, correct pinning, and hygiene on release.
2. **G2 — Drop-in:** Doctrine DBAL driver and Laravel/Eloquent connector requiring only config changes. Acceptance: upstream test suites pass (§14, §15).
3. **G3 — Typed:** One canonical type system across backends; native API hydrates readonly PHP DTOs.
4. **G4 — Concurrency:** Request multiplexing; PHP Fibers enable parallel queries from one request. Sync fallback works everywhere.
5. **G5 — Checked SQL:** Build-time verification of queries against a shadow schema + DTO/stub codegen (sqlx-style).
6. **G6 — Observability & security:** Tracing, pool metrics, slow log; credentials isolated in the engine; optional manifest-only query mode.
7. **G7 — Predictable failure:** Engine restarts and backend flaps surface as a small, typed error set with defined client recovery (§9.2, §19). No silent ambiguity about the fate of a write, ever.

## 3. Non-goals

- Not a storage engine, not a SQL rewriter, not a cache of query results.
- No ORM in Rust: identity maps, lazy proxies, object graphs, PHP-closure middleware stay in PHP. The engine's job ends where live object semantics begin.
- No read/write inference from SQL text for replica routing in v1 — routing is explicit (§7.6).
- No transparent engine-side retry of user statements — the engine reports outcomes truthfully; retry is client policy (§19.3).
- Oracle deferred (blocking OCI wrapper on a `spawn_blocking` pool, post-v1). Windows native is TCP-only best-effort (§21 D4).

## 4. Architecture overview

```
┌────────────── host ──────────────────────────────────────────┐
│  PHP-FPM workers (N)                                          │
│   ├─ ferro/client        (native typed API, Fibers-aware)     │
│   ├─ ferro/doctrine-dbal (Driver impl → client)               │
│   └─ ferro/laravel       (Illuminate Connection → client)     │
│              │  UDS /run/ferro/{build-hash}.sock              │
│              ▼                                                │
│  ferrod (Rust, tokio)                                         │
│   ├─ session layer: handshake (epoch), auth, multiplexing,    │
│   │                 flow control, PING/PONG                   │
│   ├─ SQL service: param bind, result framing                  │
│   ├─ TX service: pin management, savepoints, retry hints      │
│   ├─ pin engine: protocol signals + assist lexer (§7.2)       │
│   ├─ pools: pg | mysql | sqlite | mssql  (+ replicas)         │
│   ├─ codegen manifest store (query_id → plan)                 │
│   └─ admin/metrics: OTLP, Prometheus, slow log                │
└──────────────────────────────────────────────────────────────┘
```

One `ferrod` per host (or per pod). Clients hold one UDS connection per worker; all requests are multiplexed over it. Transactions pin engine-side to a `tx_id`, not to the client socket, so a Fiber-suspended request keeps its transaction across frames.

## 5. Transport and framing

**Transport:** Unix domain socket, path versioned by build: `/run/ferro/{schema_hash}.sock`. Deploys with changed contracts spawn a fresh daemon instance; the old one drains and exits on idle TTL (§18). TCP loopback fallback (`FERRO_ADDR`) for containers without shared sockets and for Windows dev (D4).

**Frame header** — 16 bytes, little-endian, followed by a MessagePack payload:

| field | type | notes |
|---|---|---|
| magic | u8 | `0xF7` |
| version | u8 | protocol major |
| flags | u16 | `STREAM`, `END`, `CANCEL`, `OOB_FD`, `COMPRESSED` (reserved, D11) |
| service | u16 | `01` core · `02` sql · `03` tx · `04` stream · `05` admin |
| method | u16 | per-service method id — registry in `/proto/methods.toml` |
| request_id | u32 | client-assigned, multiplexing key (§5.2) |
| payload_len | u32 | MessagePack body length |

**Handshake:** client `HELLO {client_version, type_registry_hash, manifest_hash?, pid, features}` → server `HELLO_ACK {engine_version, boot_epoch, features, pools[], type_registry_hash}`.

- `boot_epoch` (u64): unique per daemon start. Clients cache it; a changed epoch on reconnect voids all session assumptions (§19).
- A type-registry mismatch is a **hard error** (forces regen/redeploy) — this is the versioning story.
- Feature bits (engine): `MEMFD`, `LISTEN_STREAMS`, `MANIFEST`. Feature bits (client): `MEMFD_RX` (able to receive fds, §5.1), `FIBERS` (informational). Unknown bits MUST be ignored.

### 5.1 Large payloads (memfd) — honest version

Results or params above a threshold (default 1 MiB) MAY move out-of-band: the engine writes into a **sealed** `memfd` (`F_SEAL_SHRINK|GROW|WRITE|SEAL`), passes the fd via `SCM_RIGHTS`, and the frame carries `{fd_index, len, encoding}` with flag `OOB_FD`.

What this buys, precisely: **engine-side** zero-copy and strictly bounded engine memory. On the PHP side there is **one copy**: the client receives the fd via `ext-sockets` (`socket_import_stream` on the UDS stream + `socket_recvmsg` with `SCM_RIGHTS`) and reads it through `php://fd/N` — PHP userland cannot mmap. True client-side zero-copy arrives only with the optional native accelerator (D12). Requirements and gating:

- The path is Linux-only and REQUIRES the client to have advertised `MEMFD_RX` in HELLO (which the client only sets when `ext-sockets` is loaded). Otherwise the engine MUST fall back to inline credit-based streaming. No behavioral difference is observable other than throughput.
- Row streaming (§10) remains the default for cursors; memfd is for bulk single-shot payloads (COPY, large JSON/bytea).

### 5.2 Session and stream rules (normative)

- **request_id:** client-assigned u32. An id is *in-flight* from the first frame the client sends with it until the client has received a frame carrying `END` for it. Ids MUST NOT be reused while in-flight; clients SHOULD allocate monotonically and wrap. The engine MUST reject a reused in-flight id with a `Protocol` error frame on that id and MUST NOT disturb the original request.
- **Ordering:** frames for a given request_id are delivered in order; interleaving across ids is arbitrary.
- **Termination invariant:** every request is terminated by exactly one frame carrying `END` (success payload, error payload, or cancelled payload). All client state machines key off this.
- **CANCEL:** client MAY send `CANCEL {request_id}` for any in-flight id; it is advisory and idempotent. The engine propagates a backend cancel (PG cancel key, MySQL `KILL QUERY`, MSSQL attention signal) best-effort. If the request already completed, CANCEL is a no-op. The client MUST tolerate ordinary result frames arriving after it sent CANCEL, up to the terminal END — which reports either `Cancelled` or the raced-to-completion result. See §9.2 for the write-fate rule.
- **Flow control:** server→client streams are credit-based **per request**: default window 64 frames / 16 MiB (the byte window is deliberately `== MAX_FRAME_PAYLOAD`: a single indivisible row can be as large as the frame ceiling, and the client will not replenish credit before it has seen that frame, so the initial window must always fit one such frame or a large row can never be sent — M1-S5 large-row rule), replenished via `WINDOW_UPDATE {request_id, frames, bytes}`. Additionally a per-session aggregate cap (default 16 MiB, also `>= MAX_FRAME_PAYLOAD`) bounds total buffered engine output; the engine never buffers unbounded results.
- **Liveness:** core `PING`/`PONG`. Clients SHOULD ping after 30 s idle when awaiting nothing; a missed PONG deadline (2× interval) marks the connection dead and enters the reconnect loop (§19.2). `GOODBYE` announces graceful client close so the engine can distinguish drain from death.

## 6. Core SQL service

`EXEC` request:

```
{ pool, sql | query_id, params: [TypedValue], options: {
    timeout_ms?, readonly?, fetch: rows|stream|none,
    isolation?  (only meaningful inside tx),
    trace?: {traceparent} } }
```

`EXEC` response:

```
{ cols: [{name, type}], rows: [[TypedValue]] | stream_ref,
  affected: u64, last_insert_id?: TypedValue,
  warnings: [], stats: {queue_us, exec_us, rows, bytes} }
```

`queue_us` vs `exec_us` is deliberately first-class: pool wait time is the KPI that tells operators to grow `max_size` (§16).

`TX` service: `BEGIN {pool, isolation?, readonly?} → tx_id`, then `EXEC {tx_id, …}`, `SAVEPOINT`, `RELEASE`, `ROLLBACK_TO`, `COMMIT`, `ROLLBACK`. Engine-side deadlines: `idle_in_tx_timeout` (default 10 s) and `max_tx_duration` (default 60 s) roll back and release the pin, returning `Retryable{TxDeadline}`. Interaction with engine restart and write-fate rules: §19.

## 7. Pooling model

Per-pool mode: **transaction** (default), **session** (always pinned; the escape hatch), **statement** (rare, autocommit-only).

### 7.1 Pin architecture: protocol signals first, lexer assist second

Pin decisions are made **post-execution from backend protocol signals** wherever the backend can report state, with a lightweight statement lexer covering only what is text-visible but protocol-invisible. This inverts v0.1, which over-trusted the lexer.

**PostgreSQL.** The `ReadyForQuery` status byte (`I`/`T`/`E`) is authoritative for transaction state — pin/unpin for tx purposes keys off it, not off lexing `BEGIN`. `ParameterStatus` covers only `GUC_REPORT` parameters (`search_path` is *not* among them) and is treated as an assist signal, never as authority.

**MySQL / MariaDB.** Connection setup MUST enable the session trackers: `session_track_system_variables` (a **curated** list, not `'*'` — see §22.2), `session_track_state_change=ON`, `session_track_transaction_info='STATE'`, with `CLIENT_SESSION_TRACK` negotiated. The signal is **split** (M1-S6): the transaction-info status flag (`SERVER_STATUS_IN_TRANS`) is the tx AUTHORITY (`tx_status → InTx`/`Idle`, never `Failed` — MySQL has no aborted-open-tx state), and the OK-packet `session_state_info` trackers are the session-mutation AUTHORITY (`take_session_mutated`, read-and-cleared), which report mutations at the server — by design covering mutations performed *inside stored programs*. **Verification test DONE (M1-S6 Task 7, §22.2): a `SET SESSION` executed inside a procedure (`CALL p_set_session()`) taints the connection on BOTH MySQL 8.4 and MariaDB 11.8 (verified live, read-back leak-closed).** The assist lexer's unconditional `CALL`/`DO` pin (§22.2) is the conservative backstop for any tracker gap. A connection whose trackers reported no mutation and which never pinned is **known clean** (the hygiene skip that keys off this is DEFERRED — §7.2, §22.2).

**Assist lexer** (keyword classifier, not a parser) covers, and pins on: `LISTEN`/`UNLISTEN`; advisory-lock function calls in top-level SQL (`pg_advisory_lock` family without `_xact`); raw client `PREPARE`/`EXECUTE`/`DEALLOCATE` (engine-managed prepares are pool-safe and namespaced, §7.5); temp-table DDL; non-local `SET` as a backstop (PG: anything not `SET LOCAL`; MySQL: `SET SESSION` — normally the tracker catches these first); SQLite `ATTACH`/state-changing `PRAGMA`. Unknown/unclassifiable statements pin conservatively (`pin_on_unknown = true` default).

**Escape hatch:** per-pool `pin_functions = ["app_acquire_lock", …]` — statements whose text references a listed function pin for the session. This is the supported path for applications whose own server-side functions mutate session state (§7.4).

**Transaction-control SQL through the guarded statement entries — two classes, one guard (M1-S8a).** The pool's user-facing entries (`Checkout::exec`/`query`/`query_stream`) classify a statement's **LEADING** verb and treat the two classes differently, through ONE shared implementation. **Boundary** verbs (`BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ABORT`, a bare `ROLLBACK`, `PREPARE TRANSACTION`) are refused on every entry, in or out of a transaction: they change whether a transaction is OPEN — the pin AUTHORITY — so one slipping through would leave a transaction the pool believes is not open on a connection bound for the next tenant, with no `tx_id`, no actor, no deadline and no rollback-on-session-death. **Savepoint** verbs (`SAVEPOINT n`, `RELEASE [SAVEPOINT] n`, `ROLLBACK TO [SAVEPOINT] n`) pass through **iff the checkout already has a transaction open**: they cannot change transaction status (PG's `ReadyForQuery` byte does not flip on any of them) and every savepoint is destroyed by its enclosing transaction. Outside a transaction they are refused, because MySQL silently IGNORES a bare `SAVEPOINT` under autocommit. A savepoint passthrough must additionally carry **no bound parameters** and be a **lone statement**, and it runs on the raw **text** protocol — the same leaf the engine's own composed `SAVEPOINT sp_N` uses. `ROLLBACK` is the only verb in both classes; its second word decides. The classifier reads the leading verb only and is **not a parser**: a compound statement's later verbs are caught by the pin AUTHORITY (`apply_tx_status`), not by this guard. Full rationale, scope limits and proofs: §22.2 (r).

### 7.2 Hygiene: at checkout, pipelined, conditional

Hygiene runs at **checkout**, pipelined ahead of the first user statement — the round trip hides behind the user's own query instead of being paid at release. Rules:

- A connection that was **pinned** during its last lease is tainted: it gets the full reset (PG `DISCARD ALL`; MySQL `COM_RESET_CONNECTION`; MSSQL reset-on-next-RPC flag, see D1). Note both are destructive to prepared statements — accepted for tainted connections. **Caveat (known defect, M1-S3, found M1-S7):** PG's `DISCARD ALL` includes `DEALLOCATE ALL`, which also destroys the statements `tokio-postgres` caches for its own **typeinfo** (`pg_type`) lookups. The driver keeps stale handles to them and is never told, so after one full reset the *next* lookup of a not-natively-known OID on that connection fails `26000 prepared statement "sN" does not exist` — permanently, for that connection. Reachable only for CUSTOM OIDs (enums/composites/ranges); every builtin OID, and therefore every type M1-S7 ships, skips the lookup entirely. Safety is intact (`NonRetryable`, never `Indeterminate`), but the promised loud `Unsupported` degrades to a bare `26000`. See §22.2 and `docs/followups/2026-08-06-discard-all-typeinfo-cache-poisoning.md`.
- A **never-pinned** PG connection gets the targeted profile: `RESET ALL; UNLISTEN *; SELECT pg_advisory_unlock_all(); DISCARD TEMP; DISCARD SEQUENCES;` — this preserves the engine's namespaced prepared statements. (v0.1's targeted list leaked advisory locks and temp tables; this one does not. `DISCARD ALL` remains the superset.)
- A **known-clean** MySQL connection (tracker-verified) skips hygiene entirely. This is what makes the ≥ 95 % statement-cache target (§16) compatible with `COM_RESET_CONNECTION` deallocating prepares: reset only fires when something actually happened. **DEFERRED (M1-S6, §22.2):** the tracker-clean skip is not yet enabled — `clean_reset_profile()` returns `Some(Full)`, so EVERY recycled MySQL connection currently runs `COM_RESET_CONNECTION` regardless of taint (correctness over the cache target, R2). Enabling the `None`-skip waits until the tracker's in-proc coverage across all reuse-relevant session variables is proven; the split-signal + read-back leak-closed verification (§7.1, §22.2) is the first step toward it.
- SQLite: N/A (engine-owned, §7.7).

### 7.3 Statement cache

Per backend connection, LRU keyed by normalized SQL fingerprint, shared across all PHP workers by construction. PG uses named statements under an engine namespace (`__ferro_{fp}`); MySQL `COM_STMT_PREPARE`. Cache size, hit rate, and evictions exported (§13).

### 7.4 The transaction-mode contract (documented limitation)

Session state mutated **inside server-side functions/procedures** is undetectable on PostgreSQL: `set_config(…, is_local => false)`, `SET`/advisory locks executed within PL/pgSQL, never appear on the wire, and `ParameterStatus` cannot report them. No lexer fixes this; PgBouncer has the same hole. Therefore, normatively:

- Transaction mode **defines** function-side session mutation as unsupported, except for functions listed in `pin_functions`.
- Applications that need it use **session mode** for that pool.
- MySQL with trackers detects most of this class (pending the M1 verification above) and is documented as the stronger backend for transaction mode.
- User documentation MUST state this contract prominently, in the pooling chapter, with the `pin_functions` and session-mode escape hatches beside it.

### 7.5 Replicas & routing

Pools may declare `replicas = [{dsn, weight}]`; `readonly: true` on EXEC (or a read-only pool alias) routes to replicas with health/lag gating (`max_replica_lag_ms`). Ferro does **not** guess read vs write from SQL in v1 — routing is explicit from the client. Doctrine/Laravel already model read/write connections and map cleanly onto this.

### 7.6 SQLite

The engine owns the file. WAL mode, one writer serialized engine-side, many readers. This removes PHP's worst SQLite failure mode (`SQLITE_BUSY` storms under FPM) and makes SQLite a legitimate small-service backend. Online backup API exposed via admin service for snapshots.

### 7.7 Health & lifecycle

Liveness pings on idle, `max_lifetime` recycling, exponential backoff on backend outage, per-backend circuit breaker (half-open probes). `SIGTERM` → drain: refuse new checkouts, let pins finish up to `drain_deadline`, then hard-close. `SIGHUP` → config reload with pool diffing. Note the positive framing for docs: the breaker plus engine-side reconnection *shields* workers from backend flaps — a herd of FPM workers no longer stampedes a recovering database.

## 9. Canonical type system

One tagged value encoding on the wire; per-backend adapters map to native formats. PHP visible types below are what the native API hydrates; DBAL/Eloquent tiers apply their own ecosystem conventions on top (§14–15).

| Canonical | PG | MySQL | SQLite | MSSQL | PHP (native API) |
|---|---|---|---|---|---|
| BOOL | bool | tinyint(1)* | int | bit | `bool` |
| I64 | int2/4/8 | *int signed | integer | int/bigint | `int` |
| U64 | — | bigint unsigned | — | — | `int` or `Ferro\U64` if > PHP_INT_MAX |
| F64 | float4/8 | float/double | real | float | `float` |
| DECIMAL | numeric | decimal | text | decimal | `Ferro\Decimal` (string-backed) |
| TEXT | text/varchar | *text/varchar | text | nvarchar | `string` |
| BYTES | bytea | *blob | blob | varbinary | `string` (binary) |
| DATE / TIME | date/time | date/time | text | date/time | `Ferro\Date`, `Ferro\Time` |
| TIMESTAMP | timestamp | datetime | text | datetime2 | `DateTimeImmutable` (naive, policy §9.1) |
| TIMESTAMPTZ | timestamptz | timestamp | — | datetimeoffset | `DateTimeImmutable` (UTC instant) |
| UUID | uuid | binary(16)/char(36) | text | uniqueidentifier | `Ferro\Uuid` |
| JSON | json/jsonb | json | text | nvarchar | lazy `Ferro\Json` (decode on access) |
| ARRAY<T> | native | — | — | — | `array` |
| INTERVAL / INET / VECTOR | native | — | — | — | dedicated value objects |

*\* configurable legacy mappings (e.g. `tinyint(1)→bool` off for people who use it as a real int).*

**M1-S7 status — implemented end to end.** `NULL`, `BOOL`, `I64`, `U64`, `F64`, `DECIMAL`, `TEXT`, `BYTES`, `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMPTZ`, `UUID` and `JSON` are implemented **in both directions** (read *and* bind) in the PHP client and on PostgreSQL and MySQL/MariaDB — **except for four documented gaps**: the three ENGINE asymmetries below (where the engine has no such type at all) and one CLIENT-side one. The client-side gap is **`BYTES`, which is read-only from PHP**: `ExecCodec::bindOne` maps *every* PHP string to `TAG_TEXT`, so no PHP value can produce a `BYTES` param and `ParameterType::BINARY`/`LARGE_OBJECT` cannot bind at all — the ENGINE's `BYTES` bind path exists and works on both backends (`bytea`; a MySQL byte-string param), it is only unreachable from the client. The `Ferro\Bytes` / explicit binary-bind marker that closes it is a sized S8 carry, §22.2 (k)(4). `ARRAY<T>`, `INTERVAL`, `INET` and `VECTOR` remain registry constants only and stay a loud `NonRetryable{Unsupported}` (§22.2), as do the per-engine deferrals listed there. The implemented set is part of the **hashed** type registry (`/proto/types.toml` `implemented` → `registry.lock.json` → `TYPE_REGISTRY_HASH`), so an engine/client pair with different type coverage fails fast at the handshake instead of throwing mid-query on the first row of a newly-supported type. Three engine asymmetries are by design and recorded in §22.2 (e): no MySQL-family backend ever emits the `UUID` tag, a MariaDB `JSON` column classifies as `TEXT`, and PostgreSQL neither produces nor binds `U64` (PG has no unsigned integer type).

**The wire payload is canonical TEXT; the PHP column above is the native-API HYDRATION.** Every tag **added in M1-S7** except `U64` (msgpack uint) rides the msgpack `str` family carrying the canonical text defined in `proto/PROTOCOL.md` §3.2 — the M0 tags keep their native msgpack families (`NULL` = `nil`, `BOOL` = `bool`, `I64` = the signed-int family, `F64` = `float64`, `TEXT` = `str`, `BYTES` = `bin`), and that surviving `str`/`bin` split is precisely *why* the S7 payloads are text-canonical: the two families are indistinguishable in PHP after unpack, so only the tag discriminates them (§22.2 (a)). The engine renders each backend's native binary form into that policy-independent, lossless payload (a `DECIMAL`'s display scale, a 200-digit numeric, `NaN`, the ±`infinity` sentinels and a `24:00:00` time all survive it), and the client turns it into the PHP types above under the §9.1 policies. The two layers are separable on purpose: `Ferro\Client\Value\RawStringValuePolicy` hands the canonical text back verbatim for the DBAL tier (§14).

**The naive/instant rule (read and bind are symmetric).** `TIMESTAMP` hydrates to `Ferro\NaiveTimestamp extends \DateTimeImmutable` — still a `DateTimeImmutable`, so the table above stays literally true — while `TIMESTAMPTZ` hydrates to a plain `\DateTimeImmutable` in UTC. On the bind side a plain `\DateTimeInterface` is an **instant** and binds `TIMESTAMPTZ` normalized to UTC; a `NaiveTimestamp` is a **wall clock** and binds `TIMESTAMP` with its text emitted verbatim, no zone conversion. That pairing is exactly what makes a read → write-back round trip byte-stable; without the subclass every value read from a naive column and written straight back would shift by whatever zone the object carried, silently.

**A `TIMESTAMP`/`TIMESTAMPTZ` column CAN change its PHP type between rows — deliberately.** `infinity` / `-infinity` (PG), `0000-00-00 00:00:00` (a MySQL zero datetime) and a **zero-IN-date** — any value with a zero *year, month or day* component, e.g. `2026-00-05` or `2026-08-00 12:00:00`, legal wherever `sql_mode` omits `NO_ZERO_IN_DATE` (MariaDB 11's default) — are legal stored values that are **not** calendar instants. The sentinel class is therefore defined by a **zero component test, not by string equality against the four fixed forms**, which is how both codecs implement it (`ferro-backend-mysql`'s `mytext.rs`; the client's `CanonicalText::dateIsSentinel` / `timestampIsInstant` / `timestamptzIsInstant`). A `DATE` sentinel keeps its tag (it is carried inside `Ferro\Date`, ask with `isSentinel()`), but a `TIMESTAMP`/`TIMESTAMPTZ` sentinel — whose PHP type is an instant — is handed back as the **canonical text**, so such a column yields a `DateTimeImmutable` for ordinary rows and a `string` for a sentinel row. This is a deliberate exception to the "a column must not change PHP type between rows" rationale that governs the other knobs (`RawStringValuePolicy`): the alternatives are worse — throwing makes a legal column unreadable with no escape hatch, and inventing a date is precisely the silent miscast §9.1 exists to prevent. **The consequence is loud, not silent:** a sentinel row fed to a `\DateTimeImmutable`-typed DTO parameter raises `Ferro\Client\Error\HydrationException` (inside the `FerroException` contract, naming the column and its actual type), and re-binding a sentinel writes it back as `TEXT`, which PG's bind pre-flight refuses against a `timestamp` slot as a known-fate error. An application that must never see the shape either excludes sentinels in SQL or reads the column with `RawStringValuePolicy`.

**The supported calendar range is `0001-01-01 .. 9999-12-31`.** Reachable data outside it — **BC dates and years above 9999** (PG's `date`/`timestamp` span 4713 BC .. 5874897 AD) — is a loud `Unsupported` naming the year, never an invented `" BC"` suffix, negative year or 7-digit year, because `proto/PROTOCOL.md` §3.2's canonical `YYYY-MM-DD` form defines no representation for them and a guessed one would differ between the two codecs. The follow-up, when a real workload needs it, is either an extended-year/BC canonical form added to PROTOCOL.md §3.2 (and both codecs) or a per-pool opt-in raw passthrough; until then the failure is diagnosable rather than a wrong date.

### 9.1 Policies over guesses

Cross-driver ambiguity is resolved by explicit policy, not silent driver behavior: `decimal: object|string`, `naive_datetime_zone: utc|server|error`, `u64_overflow: object|string|error`, `uuid: object|string`. Defaults are the safe object forms. This is where Ferro is deliberately *better* than PDO, whose per-driver casting inconsistencies are a chronic source of production bugs.

**As shipped in M1 these four knobs are CLIENT-SIDE, not pool-level (M1-S7; §22.2).** They are a `Ferro\Client\Value\TypePolicyOptions` value object threaded `Ferro::connect(types:)` → `Connection(types:)` → the decoding `ValuePolicy`. There is no `ferrod` knob, because the S7 wire is lossless canonical text (§9 above): the engine renders a policy-**independent** payload, so nothing in the daemon could act on a `decimal=string` pool setting. Pool-level *defaults advertised to the client* via `HELLO_ACK` pool metadata are an S8 carry. The shipped semantics:

- **`decimal`** — `object` (default) → `Ferro\Decimal` (string-backed, exact); `string` → the canonical text, still validated.
- **`uuid`** — `object` (default) → `Ferro\Uuid`; `string` → the canonical lowercase text, still validated.
- **`u64_overflow`** — `object` (default) → a PHP `int` when the value fits, `Ferro\U64` above `PHP_INT_MAX`; `error` → refuse **only** the overflowing value; `string` → the decimal text for the **whole column**, not merely for overflowing values. That last one is a deliberate wart against the knob's *name*: the point of `string` is that a column's PHP type must not depend on a given row's magnitude (which is what DBAL and a `string` schema column want), so it cannot be applied per value. Choose `object` if you want the narrow behaviour the name suggests.
- **`naive_datetime_zone`** — `utc` (default) → a `Ferro\NaiveTimestamp` pinned to an explicit UTC zone; `error` → refuse the naive tag outright, scoped to `TAG_TIMESTAMP` **alone** (`TIMESTAMPTZ`/`DATE`/`TIME` still decode; an undefined scope would make whole columns unreadable with no escape hatch). **`server` is not implementable in M1** and is rejected loudly by the constructor rather than silently downgraded to `utc`: nothing on the wire carries the backend's session timezone (`HelloAck` is `[engine_version, boot_epoch, features, pools, type_registry_hash]`). It is deferred, and lands with the same `HELLO_ACK` pool metadata the S8 backend-kind/server-version carry waits on.
- **Refusals are not wire faults.** A policy refusal raises `Ferro\Client\Error\TypePolicyException`; a **malformed** payload (a `DECIMAL` that is not a number, a truncated `TIMESTAMP`) stays `ProtocolException`. The split is by cause, so the S8 DBAL `ExceptionConverter` never reports a configuration choice as a driver protocol failure. Neither is a §9.2 fate branch: both are raised **client-side — never from a wire terminal**, either *pre-send* in `ExecCodec::bindOne` (a `naive_datetime_zone=error` refusal of a naive `TIMESTAMP` param throws during `encode()`, before the request leaves the client, so nothing was executed) or *post-success* in `ExecCodec::decodeRow` (mid-row on the streamed path, after the statement already succeeded).
- **`Connection::typePolicy()` reports the options THIS connection was constructed with.** When a caller injects a ready-made `codec:` or `values:` instead (those forms carry their own embedded policy, and the three arguments are mutually exclusive), the accessor returns the **defaults** — it is a convenience for the common path, not an authoritative read of the policy actually decoding rows.

**MySQL/MariaDB sessions are pinned to `time_zone = '+00:00'` (M1-S7).** §9 maps MySQL's `timestamp` to `TIMESTAMPTZ`, a UTC instant — but the driver hands back zone-*less* date/time components, converted by the server into the *session* zone, so an instant is only definable against a known one; and under pooling an unpinned session zone would make the same column read differently per connection. Ferro therefore pins every MySQL/MariaDB session (re-applied after each `COM_RESET_CONNECTION`), on both the read and the bind side. **Visible consequence: `NOW()`, `CURDATE()` and `CURTIME()` return UTC on every Ferro MySQL connection**, which may differ from a legacy application's previous behaviour. This is the same choice Doctrine and Laravel make, and it is what keeps a pooled `timestamp` column deterministic.

**MySQL/MariaDB column classification (M1-S6, widened by M1-S7).** The MySQL backend keys every column off the wire **column metadata** (column type + flags + charset + display length), not the driver's ambiguous binary `Value`. `TINYINT(1)` (MySQL's `BOOLEAN` idiom, identified by display length 1, signed or unsigned) → `BOOL`; a wider signed `TINYINT`/`SMALLINT`/`MEDIUMINT`/`INT`/`BIGINT` and every *unsigned* integer narrower than 64 bits → `I64` (all fit losslessly); `BIGINT UNSIGNED` → `U64`; `FLOAT`/`DOUBLE` → `F64`; `CHAR`/`VARCHAR`/`TEXT` (non-binary charset) → `TEXT`; `BINARY`/`VARBINARY`/`BLOB` (binary collation 63) → `BYTES`; `DECIMAL`/`NEWDECIMAL` → `DECIMAL`; `DATE` → `DATE`, `TIME` → `TIME`, `DATETIME` → `TIMESTAMP` (naive), `TIMESTAMP` → `TIMESTAMPTZ` (a UTC instant, under the session pin above); MySQL 8's `JSON` → `JSON`; **`ENUM` → `TEXT`** (or `BYTES` on a binary collation — it takes the same charset branch every other string type takes; M1-S8a). **M1-S6's deferrals of `BIGINT UNSIGNED`, `DECIMAL`, the date/time family and `JSON` were closed by M1-S7, and `ENUM` by M1-S8a** — this paragraph previously listed them all as out of scope. An `ENUM` cell's binary-protocol value **IS** its label string in the column's charset, so carrying it as `TEXT` is lossless rather than a promotion, and it is what makes `information_schema` readable (`COLUMNS.COLUMN_KEY` and `referential_constraints.UPDATE_RULE`/`DELETE_RULE` are `ENUM`s on MySQL 8, though not on MariaDB). Still **out of scope**, and still a **loud `Unsupported`** naming the column + its MySQL type rather than a silent miscast: `YEAR`, `BIT`, `SET`, `GEOMETRY`, `VECTOR` — `SET` in particular stays out because its wire form is a **comma-joined multi-value** string, a different type rather than a longer one. Two engine facts are by design, not gaps (§22.2): a MariaDB `JSON` column is a `LONGTEXT` alias and classifies as `TEXT`, and MariaDB's native `UUID`/`INET4`/`INET6` reach the wire as `MYSQL_TYPE_STRING`/utf8mb4 and classify as `TEXT` — so no MySQL-family backend ever emits the `UUID` tag. A cell whose driver `Value` variant does not match its column kind is a client-side decode mismatch → `Backend` (NonRetryable), never `ConnectionLost` (so it can never mint a false §19.3 `Indeterminate`). This is the documented policy the S8/S9 DBAL/Eloquent suite inherits (§14–15) — a diagnosable error, not a surprise miscast. Source: `engine/crates/ferro-backend-mysql/src/rowmap.rs`.

**PostgreSQL column classification (M0/M1-S7, widened by M1-S8a with the CATALOG scalars).** The PG backend keys every column off its `RowDescription` **OID**, through one table (`oid_extract_type`) that backs both the cols-build tag gate and the per-cell extractor so the two can never drift. Alongside the §9 table's scalars, M1-S8a admits the four types PG's own catalog is written in — the ones DBAL's `AbstractSchemaManager` selects on every introspection: `name`(19) → **`TEXT`** (it is already in `String`'s `FromSql` accept list, so it folds into the existing text arm); `"char"`(18) → **`TEXT`**, but it is a **single BYTE**, rendered the way PG's own `charout` does — `'\0'` is the **empty string** (which is exactly what `pg_attribute.attidentity` holds on a non-identity column), an ASCII byte is that one character, and a non-ASCII byte is a loud `Backend` decode mismatch rather than an invented replacement character; `oid`(26) → **`I64`** (read as `u32`, widened losslessly); and `regtype`(2206)/`regclass`(2205) → **`I64`**, reporting the **numeric OID**, because under Ferro's binary result format their payload literally *is* a 4-byte OID (`regtypesend` **is** `oidsend`) and resolving it to a type NAME would require a catalog round trip the engine must not make (charter rule 6). A caller who wants the name casts in SQL — `::text` or `format_type(...)` — which is what DBAL's own introspection already does. **No new canonical tag and no `/proto` change**: every one of them lands on `TEXT` or `I64`. Still **out of scope** and still a loud `Unsupported`: `timetz`, arrays (incl. `oidvector`), `interval`, `inet`, and every enum/composite/range type (per-database CUSTOM OIDs — see §22.2 (h) and (m)). A DOMAIN is reported by PG as its BASE type, so it is supported iff that base is (§22.2 (g)). Source: `engine/crates/ferro-backend-pg/src/rowmap.rs`.

### 9.2 Normalized error taxonomy — three branches

Every backend and engine error maps to one tree, carrying the raw SQLSTATE/errno alongside:

```
Retryable      { ConnectionLost{epoch_changed: bool}, PoolTimeout, TxDeadline,
                 Deadlock, SerializationFailure, ReplicaUnavailable }
Indeterminate  { WriteUnconfirmed{cause: link_lost|timeout|engine_restart} }
NonRetryable   { Syntax, Constraint{Unique, ForeignKey, NotNull, Check},
                 Auth, QueryTimeout, Cancelled, Protocol, Unsupported }
```

**`Indeterminate` is the branch v0.1 was missing.** It is raised when a side-effecting statement was dispatched and its fate is unknown: the backend link (or the engine itself, §19) died between dispatch and response. Rules:

- Reads that die mid-flight are `Retryable{ConnectionLost}` — a read has no fate to be unsure about.
- A cancelled or timed-out **autocommit write** whose non-execution the engine could not confirm surfaces as `Indeterminate{cause: timeout}`, not `Cancelled`/`QueryTimeout`. Inside a transaction, timeout/cancel is safe: the engine rolls the tx back, and the client sees `Retryable`.
- Clients MUST NOT auto-retry `Indeterminate` unless the query's manifest entry declares `idempotent: true` (§11). Raw-SQL writes are never auto-retried.
- The engine never retries user statements transparently in any branch — it reports; the client's policy layer decides (§19.3).

DBAL's ExceptionConverter and Laravel's `QueryException` map from this one tree (§14–15), giving identical exception semantics across all backends. `Indeterminate` maps to a Ferro-specific exception class in both tiers (subclassing each ecosystem's driver-exception base) since neither ecosystem models the concept.

## 10. Native PHP client (`ferro/client`)

Pure PHP, zero required extensions; **PHP ≥ 8.2** (readonly classes). Optional accelerators, runtime-detected: `ext-msgpack` (codec hot path, `composer suggest`), `ext-sockets` (enables the `MEMFD_RX` feature, §5.1). Connection-less by design: you submit work, you never hold a connection.

```php
$db = Ferro::pool('main');

// typed hydration into readonly DTOs
$user  = $db->queryOne(User::class, 'select id, email, created_at from users where id = ?', [$id]);
$rows  = $db->query(OrderRow::class, 'select … where status = ?', [Status::Open]);

// scalars / assoc escape hatches
$count = $db->scalar('select count(*) from orders');
$assoc = $db->rows('select …');                 // array<array<string,mixed>>

// transactions are closures; scope is explicit, retry is policy
$db->transaction(function (Ferro\Tx $tx) {
    $tx->exec('update accounts set balance = balance - ? where id = ?', [$amt, $a]);
    $tx->exec('update accounts set balance = balance + ? where id = ?', [$amt, $b]);
}, Retry::onSerializationFailure(times: 3, backoff: Backoff::jitter(10, 200)));

// streaming: constant memory, credit-driven
foreach ($db->stream(Event::class, 'select … order by id') as $event) { … }

// notifications as iterators (PG)
foreach ($db->listen('jobs') as $note) { … }
```

**Hydration contract:** DTOs are `final readonly` classes with promoted constructor properties; column→property matching by name (snake→camel mapping configurable), types validated against the canonical registry at first use and memoized. No reflection per row on the fast path.

**Resilience:** the client implements the reconnect loop, epoch tracking, and retry policy of §19. The transaction closure above is the recovery surface: `Retryable` inside a closure re-runs the whole closure on a fresh connection/epoch when the policy allows.

### 10.1 Concurrency

`queryAsync()` returns a `Ferro\Future`. Under plain FPM, `await` blocks on the socket — correct everywhere, zero setup. If a Fiber scheduler is active (`Ferro\Loop::run(...)`, or Revolt/AMPHP detected), awaiting suspends the Fiber and the client multiplexes all in-flight requests over the single UDS connection:

```php
[$profile, $orders, $flags] = Ferro\await([
    $db->queryOneAsync(Profile::class, …),
    $db->queryAsync(OrderRow::class, …),
    $flagsDb->queryAsync(Flag::class, …),
]);
```

Fan-out of k queries costs ≈ max(query) + boundary overhead, not the sum. Transactions are Fiber-safe because pins follow `tx_id`, not the socket. **Octane/Swoole caveat:** Swoole coroutines and Fibers don't compose; under Octane the client runs in sync-per-worker mode (documented).

## 11. Checked SQL & codegen (`ferro` CLI)

sqlx's trick, ported: verify every query against a real schema at build time, and generate the types. The CLI is a Rust binary in the engine workspace (D10), sharing the proto and backend crates.

- `ferro schema sync` — applies the project's migrations to a disposable shadow database (or loads a committed schema snapshot).
- `ferro check` — collects queries from: `.sql` files with front-matter and `#[FerroQuery('…')]` attributes (v1); inline `Ferro::sql('…')` literals via a PHPStan extension (phase 2, D3). Each is `PREPARE`d against the shadow schema; syntax errors, unknown columns, and param-count/type mismatches fail CI.
- `ferro gen` — emits `gen/`: readonly DTO classes with native property types, PHPStan stubs, and `manifest.json`.

**Manifest schema:** `query_id → {normalized_sql, param_types, result_shape, pool, readonly: bool, idempotent: bool}`. `idempotent` defaults to `false`; it is declared in the query's front-matter/attribute and is the sole license for auto-retrying an `Indeterminate` write (§9.2, §19.3) — a natural-key upsert can declare it, a balance increment cannot.

The manifest hash participates in the handshake (§5). **Manifest-only mode** (`pools.<name>.manifest_only = true`): the engine executes only registered `query_id`s and rejects raw SQL — the injection surface collapses to zero for that pool, and compromised PHP cannot exfiltrate beyond the declared query set. Ships as a hardening option, off by default.

## 12. Security model

- UDS with `SO_PEERCRED` allow-list (uid/gid) + optional bearer token for TCP fallback.
- **Credential isolation:** DB DSNs/passwords live only in `ferrod`'s config/secret store. PHP never sees them; an FPM compromise leaks no database credentials, and with manifest-only mode cannot even issue arbitrary queries. Consequence for ecosystem tooling that shells out with credentials: §14–15 and D8.
- TLS to upstreams (rustls), per-pool CA/cert config, `sslmode` equivalents.
- memfd payloads are sealed (§5.1) and fds pass only over peer-cred-verified sockets; at-rest encryption of these buffers is out of scope for v1 (D6).
- Per-pool guards: `readonly = true` pools set backend read-only session state and reject classified writes; `max_result_bytes`, `default_timeout_ms` are pool policy.

## 13. Observability

- OTLP traces: one span per EXEC (`query_id`/fingerprint, pool, backend conn id, rows, bytes, `queue_us`/`exec_us` split), linked to the caller's `traceparent` passed in EXEC options.
- Prometheus: pool size/idle/pinned, checkout p50/p99, queue depth, pin duration histogram, **pin-cause counters** (labels: `tx, set, listen, lock, prepare, temp, unknown, pin_function`), **hygiene counters** (`skipped_clean, targeted, full`), statement-cache hit rate, replica lag, error-taxonomy counters including `indeterminate_total`, engine `boot_epoch` gauge and restart counter.
- Slow log: normalized fingerprints, redacted params by default (`log_params = never|on_error|always`).
- `ferro top`: live TUI over the admin service (current pins, longest transactions, hot fingerprints).

## 14. Doctrine tier (`ferro/doctrine-dbal-driver`)

**Goal:** existing Doctrine DBAL / ORM applications switch by configuration only. The ORM's identity map, lazy proxies, and hydrators are untouched (rows cross the wire as arrays at this tier; typed-DTO hydration is a native-API feature). The wins here are pooling, multiplexing, shared statement cache, and normalized errors.

**Surface.** Implements the DBAL driver SPI, **DBAL `^4.0` first** (D2; `^3.8` bridge is an M2 deliverable):

- `Ferro\DBAL\Driver` → `connect()` returns a `Ferro\DBAL\Connection` bound to a pool session; `getDatabasePlatform()` selects the platform from `HELLO_ACK` pool metadata + server version; `getExceptionConverter()` maps the §9.2 tree to DBAL exceptions (`UniqueConstraintViolationException`, `DeadlockException`, `ConnectionLost`, …) uniformly across backends, plus `Ferro\DBAL\IndeterminateWriteException` for the third branch.
- `Connection`: `prepare()`, `query()`, `exec()`, `lastInsertId()`, `beginTransaction()/commit()/rollBack()` → TX service frames (savepoints via DBAL's normal savepoint path); `quote()` client-side per platform (D5; discouraged, present for compat); `getServerVersion()` from handshake; `getNativeConnection()` returns the `Ferro\Client\Session` — **documented break** for code expecting a `PDO` instance.
- `Statement`/`Result`: `bindValue()` with DBAL `ParameterType`→canonical mapping; `Result::fetch*()` families backed by row frames; `rowCount()` from `affected`; streaming used automatically when the consumer iterates (`iterateAssociative()` et al. never buffer).

**Configuration:**

```php
// Doctrine / Symfony
'connections' => ['default' => [
    'driverClass' => Ferro\DBAL\Driver::class,
    'ferro' => ['pool' => 'main', 'read_pool' => 'main_ro'],
]],
```

**Semantics & compat notes:**

- `lastInsertId()`: MySQL from the OK packet of the last EXEC on the session; PG via `RETURNING` (DBAL/ORM already prefer sequences/`RETURNING`); sequence-name argument supported for PG.
- DBAL middlewares (logging, schema managers, migrations) operate above the driver SPI and work unchanged; `doctrine/migrations` runs its DDL through the same session (DDL pins per §7).
- Known incompatibilities to document: bundles calling `getNativeConnection()` expecting PDO; `pdo_pgsql`-specific COPY hacks (replaced by a first-class `Ferro\Pg\Copy` API); persistent-connection tuning advice (obsolete under Ferro); **anything shelling out to `pg_dump`/`mysqldump` with application config credentials — the credentials no longer exist in PHP** (D8: ops provisions separate dump credentials; no engine passthrough in v1). The incompat list is a first-class doc page with per-package workarounds, budgeted in M2.
- **Acceptance:** DBAL 4 functional test suite green on PG + MySQL + SQLite; ORM functional suite green on PG + MySQL. Runner scripts live in `/testkit` (§20.3).

## 15. Eloquent tier (`ferro/laravel`) — drop-in

**Goal:** `config/database.php` changes `driver` and nothing else. Models, query builder, migrations, seeds, `DB::` facade, pagination, `chunk`/`lazy`, upserts, transactions with `attempts`, and events all behave identically.

```php
'connections' => [
    'mysql' => [
        'driver' => 'ferro-mysql',      // was 'mysql'
        'pool'   => 'main',
        'read'   => ['pool' => 'main_ro'],   // optional, maps to Laravel's read/write split
        // host/username/password removed — credentials live in ferrod (§12)
    ],
],
```

**Mechanism.** A service provider registers `ferro-{mysql,pgsql,sqlite,sqlsrv}` via `Illuminate\Database\Connection::resolverFor()`. Each resolver builds `Ferro{MySql,Postgres,SQLite,SqlServer}Connection extends` the corresponding Illuminate connection class — inheriting the stock Grammar and Processor, which only build SQL strings and post-process results and therefore need no changes. The subclass overrides the execution layer:

- `select()`, `selectResultSets()`, `cursor()` → EXEC frames; `cursor()` maps to the credit-based stream (§5.2) surfaced as `LazyCollection` — `Model::lazy()`/`chunkById()` get constant-memory behavior for free.
- `statement()`, `affectingStatement()`, `unprepared()` → EXEC with `fetch: none`, `affected` returned.
- `beginTransaction()/commit()/rollBack()` and savepoint compilation → TX service; `DB::transaction($fn, attempts: 3)` maps `attempts` to the engine's retryable classes (deadlock/serialization) so retries actually re-run the closure on a fresh tx.
- `getPdo()/getReadPdo()` return a **`FerroPdoShim`** — a thin PDO-interface adapter implementing only the residual surface the framework and common packages touch (`quote`, `lastInsertId`, `inTransaction`, `exec`, `getAttribute(SERVER_VERSION)`). It exists so `ManagesTransactions` internals and ecosystem packages keep working; `getRawPdo()` throws with a pointer to this section.
- `lastInsertId` semantics identical to §14; `Schema` builder and migrations run through `statement()` unchanged.
- **Known incompatibilities to document:** `php artisan schema:dump` and `php artisan db` (both spawn native clients with config credentials, which no longer exist — D8), `spatie/laravel-backup` and similar dump-based packages, packages reaching for `PDO::pgsqlCopyFromArray` (Ferro-native `Ferro\Pg\Copy` equivalent documented). Same incompat doc page as §14.

**Acceptance:** the `illuminate/database` integration test suite green on MySQL, PG, SQLite via Ferro connections; a Laravel demo app (auth scaffolding + queues + Horizon DB metrics) runs with only the config diff above. Octane supported in sync mode (§10.1 caveat).

## 16. Performance targets (v1 exit criteria)

- Boundary overhead (client call → engine → trivial `SELECT 1` → response): **p50 < 60 µs, p99 < 200 µs** on loopback UDS, vs local PDO baseline.
- Equal-throughput upstream connection count reduced **≥ 5×** on the reference workload (200 FPM workers, pgbench-like mix).
- 10-query fan-out latency ≤ max(single query) + 2 ms under Fibers.
- Streaming a 1 GB result: client RSS bounded by window (≤ 16 MiB), engine RSS bounded by per-stream buffers.
- Statement-cache hit rate > 95 % steady-state on the reference app (made achievable by conditional hygiene, §7.2).

All targets are measured against a **recorded reference environment** — `bench/README` pins CPU model, kernel, PHP version, and JIT status; numbers are meaningless otherwise.

### 16.1 Boundary budget and the M0 decision gate

Component budget for the trivial-call path, pure-PHP client:

| component | est. µs |
|---|---|
| 2× UDS syscalls (write/read) | 2–4 |
| MessagePack encode+decode, pure PHP | 5–15 (JIT-dependent) |
| frame header pack/unpack | ~0.5 |
| engine hop (decode, pool checkout hit, dispatch) | 5–10 |
| backend `SELECT 1` round trip | 20–40 |
| hydration (memoized plan) | ~1/row |

p50 < 60 µs is reachable pure-PHP. **p99 is where pure PHP dies first** — GC pauses, JIT-less hosts, wide rows. Mitigations in order: runtime-detect `ext-msgpack` (`composer suggest`, transparent swap); header codec is a single `pack`/`unpack` either way. **Decision gate (D12): the M0 bench harness measures p99 on the reference environment with the pure-PHP codec. A miss pulls the `ext-php-rs` accelerator (frame codec + hydration, same wire contract) forward into M1.** M0 does not exit without this measurement recorded.

## 18. Deployment & lifecycle

Single static binary. **systemd (primary):** templated units — `ferrod@.service` + `ferrod@.socket`, instance name = schema hash, socket unit binds `/run/ferro/%i.sock`. Socket activation means **systemd holds the listener fd across daemon restarts**: connections arriving mid-restart queue in the backlog instead of getting `ECONNREFUSED`, which is what makes §19's reconnect story quiet in practice. Deploys: start `ferrod@{new_hash}.socket`, atomically switch a `current` symlink for tooling, old instance drains via idle TTL and exits; old and new coexist during rollout. (v0.1's single static unit could not express this — hash-versioned paths require the template form.)

Also: pod sidecar sharing an `emptyDir` socket volume. Config `ferro.toml` (pools, DSNs via env/secret refs, policies); `SIGHUP` reload, `SIGTERM` drain. Client discovers the socket by schema-hash path, then `FERRO_ADDR` fallback. Kubernetes readiness = admin `/healthz` (all pools connectable, or degraded-but-serving flag).

## 19. Engine restart & client resilience

A `ferrod` crash or deploy is a *correlated* failure — every worker at once — unlike shared-nothing PDO where connection death is uncorrelated. v0.1 hand-waved this; it is now first-class. The design goal: an engine restart is a **blip for reads and declared-idempotent writes, a clean typed error for everything else, and never a silent unknown**.

### 19.1 Epochs

`boot_epoch` arrives in HELLO_ACK and is cached by the client. On reconnect, a changed epoch means: all engine-side state (tx pins, streams, prepared handles) is gone. Type-registry hash is re-verified as always; mismatch remains a hard error.

### 19.2 Client reconnect loop

On dead socket (EOF, write failure, missed PONG deadline): reconnect with jittered exponential backoff (base 10 ms, cap 1 s, deadline default 5 s → then `Retryable{ConnectionLost}` surfaces to the caller as pool-unavailable). With socket activation (§18), restarts rarely refuse — connects block in backlog until the new instance accepts.

### 19.3 Fate rules on connection loss

For each request in flight when the link died:

- **Read** (`readonly: true`, or manifest `readonly`): `Retryable{ConnectionLost, epoch_changed}`. Auto-retried by the client when `retry_reads = true` (default), transparently, on the new epoch.
- **Autocommit write:** `Indeterminate{WriteUnconfirmed, cause: link_lost}`. Auto-retried **only** when the manifest entry declares `idempotent: true`; otherwise surfaced. Raw-SQL writes always surface.
- **In-transaction request:** the whole transaction is dead (the engine rolled it back or died with it). Closure-API users: the closure re-runs on the new epoch under the caller's retry policy — this is why the closure is the primary tx API. Explicit BEGIN/COMMIT users receive `Retryable{ConnectionLost, epoch_changed: true}` and must restart the transaction themselves.
- A `COMMIT` frame sent with no response is the one transactional `Indeterminate`: the commit may or may not have applied. Surfaced as `Indeterminate{cause: link_lost}`; never auto-retried.

Engine-side mirror: when a *backend* link dies, the engine applies the same classification (dispatched-without-response → `Indeterminate`; not-yet-dispatched → `Retryable`) and MUST NOT transparently re-dispatch (§3).

### 19.4 What the engine gives back

The same daemon that concentrates risk also absorbs it: circuit breakers, engine-side backend reconnection, and drain semantics mean a flapping database is met by one polite reconnector instead of 200 stampeding workers, and workers keep getting fast typed `Retryable` errors instead of hanging on TCP timeouts. Documentation should present this chapter as a trade made deliberately, with the mechanics above as the price paid.

The airtight fix (have `handle_begin` re-check the request `CancellationToken` immediately before `register`, rolling back + dropping the fresh conn if the session is draining) is **deferred to S7-era hardening** — it changes no wire contract and nothing downstream depends on it.

### 22.2 M1 implementation deviations

These record where an M1 slice's build intentionally differs from, or narrows/widens, the target design in the body of this spec; each is a scope note against the M1 execution design (`docs/superpowers/specs/2026-07-28-ferro-m1-execution-design.md`), not a silent change to the target spec text.

- **§7.2 hygiene profile predicate is `tainted`, not "was pinned" (M1-S3)** — §7.2's literal rule is "a connection that was *pinned* during its last lease → full reset." The shipped predicate (`docs/superpowers/plans/2026-07-28-ferro-m1-s3-conditional-hygiene.md`, S3) is instead the connection's existing `tainted` bit: a cleanly-committed transaction (`BEGIN; SELECT; COMMIT`, no session-mutating statement, no error) does **not** set `tainted` (S1's `commit_tx` clears `tx_open` and leaves `tainted` alone), so it is treated as a non-tainted recycled conn and gets the **targeted** profile, not a forced `DISCARD ALL`. This is a deliberate refinement, not a laxer reading: prepares survive checkout for clean transactions, while the targeted profile still closes every leak class the full reset would have caught. A transaction that *did* mutate session state is `tainted` by the S2 assist lexer (or by an error / aborted transaction via the S1 Err-arm / RFQ `E`) and still gets the full reset.
- **§7.2 targeted profile string deviates from this spec's authored 5-statement list (M1-S3)** — §7.2 authors the targeted profile as `RESET ALL; UNLISTEN *; SELECT pg_advisory_unlock_all(); DISCARD TEMP; DISCARD SEQUENCES;`. The shipped profile (S3) additionally runs `CLOSE ALL` and `SET SESSION AUTHORIZATION DEFAULT` ahead of that list. `CLOSE ALL` closes a gap found during S3 verification: a `WITH HOLD` cursor (`DECLARE`, session-scoped, survives `COMMIT`) is not a safe-listed leading keyword, so under `pin_on_unknown=false` a `DECLARE ... WITH HOLD` conn classifies non-tainted — without `CLOSE ALL` the cursor (and the rows it can `FETCH`) would leak to the next tenant. `SET SESSION AUTHORIZATION DEFAULT` matches `DISCARD ALL`'s separate handling of `role`/`session_authorization` (which `RESET ALL` alone does not cover); it is a reset-to-self and never errors. With both additions the shipped targeted profile is **functionally equivalent to** `DISCARD ALL` minus the two prepare-destroying statements (`DEALLOCATE ALL`/`DISCARD PLANS`, which stay omitted so namespaced prepares survive a targeted reset), with the advisory-lock release made explicit via `SELECT pg_advisory_unlock_all()`. Recommend updating §7.2's authored list itself to match in a future spec pass.
- **§7.2 "pipelined ahead of the first user statement" is deferred post-S3 (M1-S3)** — S3 ships the conditional Full-vs-Targeted profile selection and the live leak-prevention + prepares-survive proof, but not checkout-pipelined hygiene: hygiene continues to run **awaited at checkout**, exactly as before S3, only with the corrected per-state profile. The optimization is deferred to a later perf slice, gated on both a recorded bench number and the §7.3 statement cache (which is unbuilt — every query currently re-`prepare`s, so pipelining has no cached prepares to protect yet) and on not touching the fork's single-slot RFQ atomic invariant to sequence it. This is charter rule 5 (no speculative optimization), not a capability gap; see the amended S3 gate in `docs/superpowers/specs/2026-07-28-ferro-m1-execution-design.md`.
- **§4/§7 session-death teardown of an in-flight tx-scoped statement may resolve via the per-request `cancel` arm, not only via `abort` (M1-S4)** — the M1-S4 plan's T3 constraint (`docs/superpowers/plans/2026-07-28-ferro-m1-s4-fate-matrix.md` T3) states that `session/mod.rs`'s `cancel_all()` at session death must route an in-flight tx-scoped `Exec` through the actor's `abort` teardown (deregister + drop-reply) only, NOT through the new per-request rollback+tombstone+reply path. As shipped, this is not quite what happens: the actor's new per-request `cancel: CancellationToken` (`tx::TxCommand::Exec`) is, of structural necessity, the SAME token `session::registry::Registry::cancel_all()` fires (it is the one token a client's own `CANCEL{request_id}` must also reach — giving the tx actor a second, separate token here would sever that routing). `session/mod.rs::run_with_handler` calls `registry.cancel_all()` *before* `tx_registry.abort_session(session_id)` (§4 ordering, unchanged by this slice), so on session death the actor's per-request `cancel` arm can win the race against `abort`, tearing the transaction down via `TxEnd::Deadline` (rollback + tombstone + a declared `TxDeadline{Retryable}` reply) instead of `TxEnd::Abort` (rollback + deregister + a silently-dropped reply). The literal fix is a session-layer reorder or a second, distinct per-request token threaded to the actor solely for this path — both out of S4's scope (a control-flow change to the session supervisor, not a fate-matrix change) — so this is recorded as a deviation, not silently patched around. It is **benign**: traced exhaustively (see the M1-S4 Task 3 report) — exactly one `teardown()` runs either way (conn always rolled back + released, permit never leaked), the forwarding handler still declares exactly one terminal (§5.2 holds), the losing client (already disconnecting) sees `TxDeadline{Retryable}` rather than `Protocol` — safe-or-better, since the tx is already rolled back either way (no double-apply risk), and the resulting tombstone is bounded by `TOMBSTONE_CAP` and scoped to a dead, never-reused `SessionId` (§7's `abort_session` final `retain` purges it regardless of Abort vs. Deadline). The non-cancel-statement-error (e.g. `23505`) no-auto-rollback behavior (§9.2, the S6 contract) is unaffected — this deviation is scoped to the interleaving of two teardown *signals*, not to the statement-error fate rules.
- **§5.2 `default_credit_bytes` coupled to `MAX_FRAME_PAYLOAD` (M1-S5 Task 1b, user-confirmed Option B)** — the streaming DATA-channel producer's large-row hazard (a single indivisible row up to `MAX_FRAME_PAYLOAD`, but the client will not replenish a request's credit window before it has seen that frame) is closed by COUPLING the default per-request byte window to the frame ceiling: `default_credit_bytes` changed from 4 MiB to 16 MiB (`== MAX_FRAME_PAYLOAD`, `proto/methods.toml`), and `ferrod::config::Config::validate` now fail-fasts at startup if either `credit_bytes` or `session_cap_bytes` is configured below `MAX_FRAME_PAYLOAD`. This **supersedes** the earlier `config.rs` "do NOT couple `credit_bytes`/`session_cap_bytes` to `MAX_FRAME_PAYLOAD`" intent noted during S5 setup — that note predates the large-row hazard analysis; the coupling is now deliberate and enforced, not accidental.
- **§5.2 streamed DATA + terminal share ONE ordered writer conduit; the priority-split second channel is deferred (M1-S5 Task 4a)** — the S3 `writer.rs`/`session/mod.rs` doc comments anticipated a *second, credit-limited data channel with control prioritized over data* for streamed result frames. As shipped (M1-S5 Task 4a), streamed HEAD/DATA frames and the request's terminal `END` instead share the SINGLE existing control channel, whose item became `ControlMsg { frame: OutFrame, cap: Option<CapReserve> }` (an `OutFrame` plus the optional per-session cap guard the writer drops after the write). This is what makes the streamed-request ordering invariant (a request's terminal never overtakes its own DATA) hold for free: DATA is enqueued during the handler run, the terminal only after (via the supervisor's already-reserved permit), so FIFO on the one channel puts the terminal last — no second channel and no cross-channel priority logic needed. The priority-split two-channel design is **DEFERRED** (charter rule 5 — no speculative throughput work before the gate); `writer::run`'s `tokio::select!` loop shape is retained so it can be reintroduced later without a rewrite. The per-session aggregate cap (`SessionCap`, §5.2) is released exactly once, when the writer drops the `ControlMsg` after the frame is written — so reserved bytes bound the bytes actually buffered toward the socket, not merely the enqueued ones.
- **§9.2/§19.3 MySQL statement-timeout errno DIVERGES between MySQL and MariaDB; the fate map keys on `errno`, not SQLSTATE (M1-S6 Task 4)** — the MySQL backend's `error_map` (`engine/crates/ferro-backend-mysql/src/error_map.rs`) classifies a `mysql_async::ServerError` by its **`errno`**, not its five-character SQLSTATE, because MySQL's SQLSTATE is too coarse to carry the §9.2 branches: a deadlock (`1213`) is SQLSTATE `40001` but a lock-wait timeout (`1205`) is the catch-all `HY000`, so a "class-40 ⇒ Retryable" heuristic (correct for PG) would silently miss `1205`. The **statement-timeout event has a different errno on each engine**: MySQL raises `3024` (`ER_QUERY_TIMEOUT`, from `MAX_EXECUTION_TIME`) while MariaDB raises `1969` (`ER_STATEMENT_TIMEOUT`, from `max_statement_time`); a `KILL QUERY` (this backend's out-of-band cancel) raises `1317` (`ER_QUERY_INTERRUPTED`) on both. All three are mapped to `errc::CANCELLED` so the **UNCHANGED** S4 `fate.rs::is_57014` override (which fires on `code == errc::CANCELLED`) yields the §19.3 cell (autocommit write → Indeterminate, in-tx → Retryable, read → Cancelled) with **no `fate.rs` edit** — the direct analog of PG's SQLSTATE `57014`. *[CLOSED by M1-S8a Task 3 — see (o) below: `PoolError::Sql` now carries an `errno: Option<i32>` slot, this module fills it from `se.code`, and `fate.rs` passes it to `ErrorPayload.errno` verbatim; the raw errno is now BOTH the classification key and a wire field.]* The raw SQLSTATE + server message are preserved verbatim on every arm. The T3-review fallback fix is also here: an unrecognized server error no longer maps to `errc::PROTOCOL` (reserved for a wire-protocol fault) but to a generic non-retryable SQL code (`errc::SYNTAX`, the broadest "server rejected this statement" NonRetryable bucket) — with a duplicate key (`1062`) mapped precisely to `errc::UNIQUE`.
- **§7/§20.1 the daemon pool registry is heterogeneous; `kind` is inferred from the DSN scheme; MySQL `fetch:stream` is deferred to M1-S7 (M1-S6 Task 5)** — *[SUPERSEDED by (n) below: MySQL streaming did NOT land in M1-S7 and is deferred out of M1-S8a as well; (n) records the structural cause, the ONE capability authority that now gates it, and the fact that the refusal is no longer restated per-arm]* — — `ferrod`'s `PoolRegistry` (`engine/crates/ferrod/src/pools.rs`) changed from a monomorphic `HashMap<String, Pool<PgBackend>>` to `HashMap<String, AnyPool>` where `AnyPool { Pg(Pool<PgBackend>), Mysql(Pool<MysqlBackend>) }`, so a `mysql://`/`mariadb://` DSN builds a `Pool<MysqlBackend>` and a `postgres://`/`postgresql://` DSN a `Pool<PgBackend>`. There is NO separate `kind =` config knob: `config::infer_pool_kind` reads the DSN scheme (the substring before `://`, case-insensitive; unknown/empty → Postgres default with a warn) and `PoolSpec` carries the resulting `PoolKind`. Dispatch is a two-arm `match AnyPool` at each `registry.get` site in `services::sql`, each arm calling ONE generic body — `run_exec_on_pool<B: PoolBackend>` (autocommit EXEC, extracted verbatim from the old inline `handle_exec` body) and `begin_on_pool<B>` (TX BEGIN, extracted from `handle_begin`); the tx actor (`actor::run<B>`) and `TxRegistry` (backend-agnostic command channels) were already generic, so the MySQL tx path spawns a `Checkout<MysqlBackend>` actor with no further change and PG's paths are byte-for-byte unchanged. - **§9/§9.1 canonical type coverage as SHIPPED — the slice-wide M1-S7 entry** (supersedes and folds in the Task 6 note) — S7 takes `U64`, `DECIMAL`, `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMPTZ`, `UUID` and `JSON` from registry constants to working end to end on PostgreSQL and MySQL/MariaDB, in both directions, with the §9.1 policies. Where the build differs from, narrows, or widens the design in the body above:

  **(a) The wire payload is TEXT-CANONICAL, not a native binary or a msgpack map/ext (USER-DECIDED).** Every S7 tag rides the msgpack `str` family carrying the canonical text of `proto/PROTOCOL.md` §3.2; `U64` alone rides the uint family. *Why:* PHP's pure decoder (`PurePacker`) cannot decode msgpack **maps or ext types at all** and §2 of PROTOCOL.md bans ext outright; `str` and `bin` are **indistinguishable in PHP after unpack** (the TypedValue tag is the only discriminator), which would force a `list<int>` special case and make the payload un-round-trippable through the golden-vector JSON; and text is the only form that preserves what actually matters — a `DECIMAL`'s **display scale** (`1.10` ≠ `1.1`, which DBAL string-compares), a 131 072-digit PG numeric, `NaN`/`±Infinity`, PG's legal `24:00:00`, and a MySQL `TIME`'s ±838 h signed range. The codecs move that text verbatim and validate nothing beyond UTF-8: the rendering decision lives in the backend, where the source format is known.

  **(b) The implemented-tag SET is part of the hashed registry (USER-DECIDED).** `/proto/types.toml` gained a real, parsed `implemented` list (replacing the dead, never-parsed `m0_scalar` key) that feeds `registry.lock.json` and therefore `TYPE_REGISTRY_HASH`. An engine/client pair with different type coverage now fails **fast at the handshake** with a registry-mismatch error instead of throwing a confusing `ProtocolException` mid-query on the first `DECIMAL` row. The list is sorted on parse so a cosmetic reorder cannot mint a spurious handshake failure. Because the hash is a *claim of coverage*, the acceptance gate (`engine/crates/ferrod/tests/types_e2e_it.rs`) DERIVES its per-tag assertions from that same list and fails if any declared tag is not both produced and consumed live.

  **(c) MySQL/MariaDB sessions are pinned to `time_zone = '+00:00'`; `NOW()`/`CURDATE()`/`CURTIME()` are UTC.** Forced by §9 mapping MySQL `timestamp` → `TIMESTAMPTZ` (a UTC instant) while the driver hands back zone-*less* components the server converted into the *session* zone — and required for pooling determinism, since an unpinned zone makes the same column read differently per connection. The pin is re-applied after every `COM_RESET_CONNECTION` and is what makes both the read renderer and the typed date/time **bind** truthful; the two are coupled (remove the pin and every `TIMESTAMPTZ` write silently shifts). The UTC `NOW()` is a visible drop-in behaviour change for a legacy application, and it is the same choice Doctrine and Laravel make.

  **(d) The naive/instant bind rule.** `TIMESTAMP` hydrates to `Ferro\NaiveTimestamp extends \DateTimeImmutable`; a plain `\DateTimeInterface` **binds** as `TIMESTAMPTZ` (an instant, normalized to UTC) while a `NaiveTimestamp` binds back as `TIMESTAMP` verbatim. The subclass exists solely as that discriminator — without it, every value read from a naive column and written straight back would shift by whatever zone the object carried, silently. MySQL's temporal params are bound as **typed** `MYSQL_TYPE_DATETIME`/`TIME` components, never as canonical text: both engines reject a `Z`-suffixed datetime literal (MySQL 8 `1292` under `STRICT_TRANS_TABLES`, MariaDB rejects offsets outright).

  **(e) Documented per-engine asymmetries (measured, by design — promoting any of them would be the silent miscast charter rule 6 forbids).** **MySQL 8 has no native UUID type** — `BINARY(16)` stays `BYTES`, `CHAR(36)` stays `TEXT`. **MariaDB's native `UUID`/`INET4`/`INET6` reach the wire as `MYSQL_TYPE_STRING`/utf8mb4**, byte-indistinguishable from a `CHAR(36)` without extended metadata the driver does not expose, so they classify **`TEXT`** (not `Unsupported`, which is what the S7 plan originally predicted). **MariaDB `JSON` is a `LONGTEXT` alias plus a `json_valid()` CHECK** and likewise classifies **`TEXT`**, so S8's DBAL `json` mapping must be designed against that. Net rule: **no MySQL-family backend ever emits the `UUID` tag**, and the `JSON` tag is MySQL-8-only. Both engines still *consume* `UUID`/`JSON` params (bound into `CHAR(36)`/`LONGTEXT`), which the acceptance gate exercises. Separately, **MySQL 8's default `sql_mode` includes `NO_ZERO_DATE`/`NO_ZERO_IN_DATE`** while MariaDB 11's does not, so writing the legal-but-zero `'0000-00-00'` sentinel on MySQL needs an explicit per-statement `SET SESSION sql_mode = ''` (which the live suite does, on both engines, rather than skipping the case on one). **And the third asymmetry is PostgreSQL's: PG has no unsigned integer type, so `U64` is neither PRODUCED nor BOUND there.** No `RowDescription` OID classifies as `U64` (`ferro-backend-pg`'s `rowmap.rs` has no arm for the tag), and on the bind side `PgU64Text::accepts` is `false` for EVERY type (`engine/crates/ferro-backend-pg/src/bind.rs`) — a deliberate **known-fate, pre-send rejection** rather than a widening guess, because `int8` cannot hold the top half of the `u64` range and `numeric` would silently change the column's type semantics.   **(j) Two consequences of the value objects that S8 must plan around.** *A `TIMESTAMP`/`TIMESTAMPTZ` column can change its PHP type between rows* — a `DateTimeImmutable` normally, the canonical TEXT on a sentinel (`infinity`, a MySQL zero datetime) — which is a deliberate exception to the "a column must not change PHP type between rows" rationale (§9); the failure is LOUD (a `HydrationException` from the DTO path, a known-fate bind refusal on write-back), never a silent miscast. *And MySQL's bind pre-flight is CANONICAL-SHAPE, not type-directed*: `COM_STMT_PREPARE` exposes no inferred parameter types, so there is no `accepts`-style per-slot check the way PG has one — a canonical `TEXT` param binds against ANY column and a mismatch is reported by the SERVER as an ordinary NonRetryable SQL error. What the engine DOES pre-flight client-side is arity plus each payload's canonical shape: a payload with no MySQL representation (PG's `infinity` / `NaN`, an over-range `TIME`) is refused **before the statement is sent**, as a known-fate `Sql{Unsupported}` — because deferring it to the server is only safe under `STRICT_TRANS_TABLES`; under a permissive `sql_mode` (which Doctrine never sets) the server silently COERCES it to `0000-00-00` / `838:59:59` / `0` instead of erroring, which would be a silent corrupt write (§22.2, measured on both engines).

  **(l) Fix round 1 — the MySQL non-canonical bind branch is a PRE-SEND rejection, because a permissive `sql_mode` COERCES rather than errors (Task 8b review).** As first built, `ferro-backend-mysql`'s `bind.rs` passed a non-parseable canonical payload through as a byte-string param, on the reasoning that the server would then raise its own clean, known-fate error.   **(m) Fix round 2 — SHIPPED DEFECT: PG's full hygiene profile (`DISCARD ALL`) permanently poisons `tokio-postgres`'s typeinfo statement cache, so a custom-OID `Unsupported` degrades to a bare `26000` (belongs to M1-S3, surfaced by M1-S7 Task 9, re-characterised by the S7 acceptance review).** `DISCARD ALL` includes `DEALLOCATE ALL`, which destroys the prepared statements the driver caches internally for its **typeinfo** (`pg_type`) lookups — the queries it issues to resolve an OID it does not know natively.   **(n) MySQL/MariaDB row streaming (`fetch:stream`) is DEFERRED out of M1-S8a — with its real cause, and one refusal authority.** On a MySQL-family pool `fetch:stream` is refused OUTRIGHT (a known-fate `Unsupported`, never a mid-stream error), so the S8b DBAL tier's `iterate*()` must **stream on PostgreSQL and fall back to a buffered `fetch:rows` on MySQL** — a documented asymmetry, not a defect (buffering is correct, just memory-hungry). The blocker is structural, not effort: every `mysql_async` streaming entry point BORROWS the connection (`QueryResult::stream`, `stream_and_drop`, `Queryable::exec_stream`, `Query::stream`), and while the OWNED-`Conn` route does type-check (`ResultSetStream<'static,'static,'static, Row, BinaryProtocol>` satisfies `Send + 'static`, proven live), there is **no public way to recover the `Conn` from a finished stream** — no `into_inner`, no accessor (`query_result` is a private field, `QueryResult.conn` is private, `Connection.inner` is `pub(crate)`), and **dropping the stream closes the connection**. An implementation therefore needs a THIRD vendored-fork divergence (today the fork carries exactly one Ferro edit) *and* a restructure of `Checkout::finalize_stream`, which reads `tx_status(&B::Conn)` **synchronously** after the drain and has no way to be handed a connection back through the `BackendRows` trait. The GAT alternative is not type-expressible: `RowStreamHandle` holds `&'a mut Checkout<B>` **and** `B::RowStream`, so a conn-borrowing stream makes it self-referential (the in-tree E0505 precedent for this exact class is recorded at `ferrod/src/services/sql.rs`'s tx-scoped streaming comment). **Two measured facts any future implementation must honour:** (1) `ResultSetStream::affected_rows()` returns the **PREVIOUS statement's** count — `setup_stream` snapshots the OK packet *before any row is read*, measured as `3` and `1` in two independent probes — so `BackendRows::rows_affected()` MUST read `Conn::last_ok_packet()` **post-drain**, never the stream's own accessor, or the engine ships a fabricated row count; and (2) the post-drain terminator for a MySQL SELECT reports `affected = 0` where PG's command tag reports the **row count**, a cross-backend divergence for `Statement::rowCount()`. **What M1-S8a DID fix:** the capability is now ONE authority — `PoolBackend::supports_row_streaming()` (default `true`, `false` for MySQL) — read by BOTH the autocommit and the tx-scoped EXEC arms through ONE terminal constructor (`services::sql::stream_unsupported`). Previously only the autocommit arm guarded (on a restated `matches!(pool, AnyPool::Mysql(_))`), so a **tx-scoped** stream was refused AFTER checkout + BEGIN, inside `Checkout::query_stream`'s Err arm, which **force-taints the pinned transaction connection** — a needless taint for a request that never should have been dispatched. **The cost of that taint is currently ZERO, and this entry originally overstated it (corrected by the M1-S8a Task 1 review):** `MysqlBackend::clean_reset_profile()` returns `Some(ResetProfile::Full)` unconditionally (`ferro-backend-mysql/src/conn.rs:329-331`), and the recycle path computes `if tainted { Some(Full) } else { clean_reset_profile() }` (`ferro-pool/src/pool.rs:160-164`) — so on a MySQL-family pool **both branches already run the full `COM_RESET_CONNECTION`**, taint or no taint, and `tx_open` is cleared by the actor's COMMIT/ROLLBACK regardless. The taint becomes a real per-recycle cost only once the deferred tracker-clean `None`-skip (R2, M1-S6 Task 7 (b)) lands and a clean connection can legitimately skip the reset. Proof: `ferrod`'s `mysql_it.rs::mysql_stream_is_refused_identically_on_both_arms_and_the_tx_survives`, which asserts the observed terminal against the daemon's own `stream_unsupported()` constructor (so a late, backend-declared refusal is RED) and that exactly ONE frame follows the tx-scoped request (charter rule 4).

  **(o) The vendor `errno` now rides the wire (M1-S8a Task 3) — MySQL/MariaDB only, `None` on PG by construction.** `PoolError::Sql` gained an `errno: Option<i32>` slot (`ferro-pool/src/error.rs`), filled at exactly ONE producing site — `ferro-backend-mysql`'s `error_map::map`, from `mysql_async::ServerError.code` (a `u16`, widened losslessly) — and passed to `ErrorPayload.errno` **verbatim** by `ferrod`'s `services::fate::classify_fate`, the ONE place a `PoolError` becomes a wire error.   **(q) Catalog + `ENUM` type coverage — the schema-introspection blocker, closed on BOTH engine families (M1-S8a Task 6).** DBAL's `AbstractSchemaManager` (and `doctrine/migrations`) run catalog SQL constantly, and it failed on both. **PostgreSQL:** `pg_type.typname` is `name`(19), `pg_attribute.attidentity` is `"char"`(18), `pg_class.oid` is `oid`(26) and `atttypid::regtype` is `regtype`(2206) — all four were a loud `Unsupported`, so DBAL 4.4.4's whole `selectTableColumns` statement was unreadable. **MySQL/MariaDB:** `ENUM` was rejected outright. Everything here maps onto **EXISTING** canonical tags — `TEXT` and `I64` — so there is **no new tag and no `/proto` change**; the mappings and their rationale are in §9's two classification paragraphs (`"char"` is one BYTE whose `'\0'` renders as the empty string; `reg*` report the numeric OID because their payload IS an OID and resolving the name would need a catalog round trip). **The MySQL correction that shaped the work:** `MYSQL_TYPE_ENUM` **never reaches the client**. The standalone `ColumnType::MYSQL_TYPE_ENUM` arm is fixed too, as **defence in depth** against a server or driver version that does send the dedicated code — but it is deliberately covered by the OFFLINE `column_kind` unit tests ONLY, because no live traffic can reach it and a live test aimed at it would be a guard that CANNOT FAIL. That is recorded rather than papered over, and it was measured: restoring only that arm leaves every live test GREEN and reddens only the offline test. **`SET` stays a loud `Unsupported` in both spellings** — its wire form is a comma-joined MULTI-value string, a different type rather than a longer one — and `ENUM` was dropped from `unsupported()`'s trailing "Deferred: …" list, which is what makes the live `SET` assertion falsifiable at all (that tail names every deferred type, so a bare `contains("SET")` was green for a `YEAR` column; the discriminating substring is the interpolated head `"MySQL SET ("`). **The live gate is `ferrod`'s `catalog_it.rs`**, on PostgreSQL 17 + MySQL 8.4 + MariaDB 11.8. Its assertions are DERIVED — for every column a query returns, the tag `HEAD` promised must equal the tag the producer emitted, swept over every non-`NULL` cell of every row with the compared-cell COUNT asserted against a measured number so an all-`NULL` result cannot satisfy it vacuously. The PG arm runs **DBAL 4.4.4's verbatim `selectTableColumns` SQL** (transcribed, not depended on — S8a takes no composer dependency) beside an explicit per-type query. **The MariaDB arm is driven through a USER `ENUM(...)` column, not through `information_schema`, and that is load-bearing:** MariaDB's `COLUMN_KEY` is a `MYSQL_TYPE_VAR_STRING`, not an `ENUM`, so it read fine before this slice — measured under the pre-fix classifier, the `information_schema` read is RED on MySQL and **GREEN on MariaDB**, which would have made a MariaDB `information_schema` assertion prove nothing. A user `ENUM` column is `MYSQL_TYPE_STRING | ENUM_FLAG` on BOTH engines and goes RED on both. Every guard was mutation-proven in both directions, including the compiler-invisible one: promising `"char"` as `I64` in `oid_to_tag` while the extractor still emits `Value::Text` compiles cleanly and is caught only by the derived live assertion.

  **(r) Savepoint SQL passes through INSIDE a transaction; a LEADING boundary verb never does (M1-S8a Task 7).** The guarded `Checkout` entries (`exec`/`query`/`query_stream`) used to refuse every transaction-control verb uniformly, which made Doctrine's nested transactions impossible: `Doctrine\DBAL\Connection` implements them by executing the literal strings `SAVEPOINT DOCTRINE_<n>` / `RELEASE SAVEPOINT …` / `ROLLBACK TO SAVEPOINT …` as PLAIN SQL through `exec()`, not through a driver API. The guard is now two-class (`pin::TxControlClass`) and shared by all three entries through ONE `Checkout::guard_tx_control` (before this it was copy-pasted three times, which is how an entry could have been added with a subtly different rule). **Boundary verbs** (`BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ABORT`, a bare `ROLLBACK`, `PREPARE TRANSACTION`) stay refused on every entry, in or out of a transaction: they change whether a transaction is OPEN — the pin AUTHORITY — so one slipping through would leave a transaction the pool believes is not open on a connection that then goes back to the pool for the next tenant, with no `tx_id`, no actor, no deadline and no rollback-on-session-death. **Savepoint verbs** (`SAVEPOINT n`, `RELEASE [SAVEPOINT] n`, `ROLLBACK TO [SAVEPOINT] n`) are allowed **iff the checkout already has a transaction open**, because they cannot change transaction status (real Postgres's `ReadyForQuery` byte does not flip on any of them — the engine's own `leading_tx_verb` model has classified them "preserve" since M1-S1) and because every savepoint is destroyed by the enclosing transaction's commit or rollback, which the tx actor owns on every exit path. **Outside a transaction they are still refused, and NOT for symmetry:** MySQL silently IGNORES a bare `SAVEPOINT` under autocommit — no transaction is started and the savepoint has no effect — so delegating to the server would hand the caller a rollback point that does not exist. (`ROLLBACK TO`/`RELEASE` under autocommit are already loud — measured `1305`/`42000` on MariaDB, `25P01` on PG; the rule covers all three because a rule that is loud for one verb and delegated for two is unreasonable-about, and PG is silent for none of them.) `ROLLBACK` is the only verb in both classes; its SECOND word decides. **`ROLLBACK [WORK|TRANSACTION] TO …` is legal PG that this two-word scan calls Boundary and therefore REFUSES** — a false refusal in the safe direction, and no DBAL platform emits it.

  **A savepoint passthrough is ROUTED to the raw TEXT leaf (`PoolBackend::simple_query`), not to the prepared/extended path — a DEVIATION from the Task 7 plan, forced by a measured fact the plan did not have.** MySQL 8 cannot run these statements on the prepared path at all: measured on 8.4.11, `COM_STMT_PREPARE` of `SAVEPOINT` / `ROLLBACK TO SAVEPOINT` / `RELEASE SAVEPOINT` fails with errno **1295** ("This command is not supported in the prepared statement protocol yet"), while MariaDB 11.8 and PG 17 accept all three. Since `ferrod`'s EXEC path (autocommit and tx-scoped alike) runs user SQL through `Checkout::query`, relaxing the guard alone would have left DBAL's nested transactions dead on the single most important DBAL backend — green on MariaDB and PG, red only on MySQL 8, which is exactly the shape of bug a single-engine test lane ships. The routing is also the consistent choice: a savepoint takes no parameters and returns no rows, so the prepared protocol buys nothing, and passthrough savepoints now run on the SAME leaf as the engine's own composed `SAVEPOINT sp_N` (`Checkout::tx_control`). Two REFUSALS make the routing safe, both strictly stricter than the old behaviour: a savepoint passthrough may carry **no bound parameters** (the text leaf cannot bind, and silently dropping them would be the miscast charter rule 6 forbids) and must be a **lone statement** (`pin::is_lone_statement` — no `;` beyond an optional trailing one; conservative, so a `;` inside a quoted identifier is refused too). `query_stream` refuses savepoints outright even inside a transaction: a savepoint returns no result set, so there is nothing to stream.

  **SCOPE OF THE GUARD, stated precisely because the obvious stronger claim is false.** It classifies the statement's **LEADING** verb only. A COMPOUND statement is not parsed: measured on MySQL, where `CLIENT_MULTI_STATEMENTS` is negotiated, `SELECT 1; COMMIT` succeeds and leaves `tx_status = Idle`, and `SAVEPOINT s; START TRANSACTION` succeeds and leaves `InTx`. So the guard may NOT be described as refusing boundary verbs "unconditionally on every entry" — the truthful claim is "refused when they LEAD the statement". This is **pre-existing** behaviour and it is **not a leak**: `apply_tx_status` reads the real post-statement status off the protocol signal after every statement, so the pin engine still sees the open transaction and still pins/taints the connection — the guard is a diagnostic front door, the protocol signal is the authority. What M1-S8a adds is that a statement may now also LEAD with a savepoint verb, which is a new vector aimed at that same guard; it is closed for the savepoint class specifically by the lone-statement rule above (`SAVEPOINT s; COMMIT` is refused, live-proven on PG, MySQL and MariaDB), so the savepoint allowance does not widen the pre-existing compound exposure. The classifier's unit table pins the compound cases explicitly, including `("SELECT 1; COMMIT", None)`, so a later slice that decides to parse compound statements must change that row deliberately.

  **Known interaction, documented not fixed:** the engine's own `SavepointStack` (the `SERVICE_TX` `SAVEPOINT`/`RELEASE`/`ROLLBACK_TO` API, which composes engine-owned `sp_N` names) does not observe passthrough savepoints, so MIXING the two forms inside one transaction can leave that stack disagreeing with the server. The DBAL tier uses passthrough exclusively. **Known cost, documented not fixed:** a passthrough savepoint is client SQL, so it reaches the §7.1 assist lexer, whose safe-list does not contain `SAVEPOINT`/`RELEASE`/`ROLLBACK`; under the default `pin_on_unknown = true` it therefore taints the connection (`PinCause::Unknown`), costing one extra hygiene reset per transaction that uses savepoints. That is the conservative direction (charter rule 5) and is left for a later perf slice to narrow by safe-listing the savepoint verbs in `ferro-classify`.

  Proof: `ferro-pool`'s `pin::tests::s8a_tx_control_class_splits_boundary_from_savepoint` (the classifier table, incl. case/whitespace/comment/quoted-identifier and compound rows) and `s8a_is_bare_tx_control_is_unchanged_from_pre_s8a` (the pre-S8a behaviour written out by hand, so it is not the tautology `is_bare_tx_control(x) == tx_control_class(x).is_some()` would have been); `ferro-pool`'s `tests/query_guard.rs` guard matrix over all three entries × both classes × both transaction states, plus the compound/params refusals; and live on PG 17, MySQL 8.4 and MariaDB 11.8 — `ferrod`'s `tx_it.rs` / `mysql_it.rs` `savepoint_sql_passes_through_inside_a_transaction` (a read-back showing the rolled-back row absent: `[1, 3]`), `boundary_sql_stays_refused_inside_a_transaction` (nine disguised boundary spellings plus `SAVEPOINT X1; COMMIT`, all refused, the transaction still usable afterwards) and `savepoint_sql_outside_a_transaction_is_refused`.

  **(p) The PG narrowing bind landed (M1-S8a Task 4) — `I64` → `int2`/`int4`/`int8`, `F64` → `float4`/`float8`, with the range check in the PRE-FLIGHT.** `bind::accepts` was `Type`-IDENTITY through the concrete `ToSql` (`<i64 as ToSql>` accepts `int8` ONLY, `<f64 as ToSql>` accepts `float8` ONLY), so a PHP `int` bound against an `int4`/`serial` PK was a hard `NonRetryable` refusal — the single highest-frequency DBAL blocker, hit by every insert into a `serial` and every identifier lookup. Two newtypes (`PgInt`, `PgFloat`) now write the **native binary** form for each width (delegating to `<i16/i32/i64>` and `<f32/f64>`, not re-rendering a decimal string PG would have to re-parse), and the pre-flight became `bind::check_param(v, ty) -> Result<(), String>` so a refusal carries an operator-facing REASON; `accepts` is retained verbatim as `check_param(..).is_ok()` so every existing call site and the directional lockstep proof read the SAME predicate. **The value-aware range gate is the load-bearing half.** `ToSql::accepts` sees only the `Type`, so a narrowing overflow is invisible to it; `check_param` sees the `Value`, and refuses an `i64` the target width cannot hold (`2147483648` against `int4`) and a FINITE `f64` that would become `inf` in `float4` (`1e39`) — a silent corrupt write. Both are **pre-send, known-fate `Sql{Unsupported}`** rejections naming the offending value, and both carry `errno: None` (no server answered). **Doing this in `to_sql` instead would be the defect, and the mechanism is MISCLASSIFICATION, not transmission:** `encode_bind_raw` serialises every param into a local buffer BEFORE anything touches the socket, so a `to_sql` failure means the statement provably never left the process — but it surfaces as `Error::to_sql(..)`, whose `as_db_error()` is `None`, which `ferro-backend-pg`'s `is_session_fatal` reads as a transport failure → `PoolError::ConnectionLost` → which §19.3 turns into `WriteUnconfirmed{Indeterminate}` on a sent, non-readonly, non-in-tx op. A statement that never left the process would then be reported as a write of UNKNOWN fate. §19.3's directional rule is therefore intact and mechanically proven: the pre-flight is STRICTER than the boxed impl (exactly as strict for the integer widths, strictly stricter for `float4`), never looser. **Precision loss WITHIN the REPRESENTABLE `f32` range is accepted and is not a miscast** — it is the column's own precision, and near the upper boundary PG's own input parser rounds a text literal identically (`3.4028235004135232e38` maps to the same `f32` in both). **Correction (Task 4 acceptance review, folded into Task 5's commit): the `float4` gate originally refused only OVERFLOW, and the UNDERFLOW mirror was a shipped silent corrupt write.** Measured live on PG 17 through the real bind path: `F64(1e-46)` bound to a `float4` returned `Ok(1)` and stored `0.0` (and `-0.0` for the negative), while PG's own parser on the identical literal `'1e-46'` returns `22003 "1e-46" is out of range for type real`. `check_range` now also refuses a finite NON-ZERO `f64` that truncates to zero in `f32`, with a message naming the value and the corruption it prevented. The boundary is REPRESENTABILITY, not normality: `1e-45` still binds, landing on the smallest `f32` subnormal (`1.401298464324817e-45`) — byte-for-byte what PG stores for `'1e-45'`, which PG accepts. **Why the shipped proofs missed it, which is the reusable lesson:** the directional lockstep rule was never violated — `check_param` and `to_sql` AGREED to truncate — so a cross-product proof over `accepts`-vs-impl is STRUCTURALLY blind to this class. It is a SEMANTIC hole (the engine disagreeing with the database it fronts), and the guard for it is a value-level assertion (`s8a_out_of_range_narrowing_is_refused_before_send`) plus a live assertion that PG's OWN parser refuses the same literal, both mutation-proven in two directions (removing the condition goes RED; making it over-strict — refusing every subnormal — also goes RED). **Guards.** The cross-product lockstep proof now drives the out-of-range magnitudes (`i64::MAX`, `i32::MAX+1`, `i16::MAX+1`, `1e39`, `NaN`) and goes RED if the range gate is removed — mutation-proven, and proven load-bearing by the converse mutation (shrink the fixture and the same broken gate stays GREEN). Because `every_variant()` is a hand-written `Vec` whose length assertion is a TAUTOLOGY with respect to a MISSING variant, a compile-forced `_exhaustive(v: &Value)` match with **no `_` arm** now lives beside it, so a 15th `Value` variant breaks the build (proven by adding one). `every_target_type()` deliberately gets no such guard and says so in-source: `tokio_postgres::types::Type` is external and open, so no exhaustive match over it exists and behavioural growth plus mutation is the only available guard. Proven live on PostgreSQL 17: `ferro-backend-pg`'s `pg_query_it::query_i64_against_int4_is_known_fate_not_connection_lost` (an in-range `I64` now inserts into an `int4` PK and reads back; an out-of-range one is refused pre-send with `errno: None`) and `ferrod`'s `sql_exec_it::exec_wrong_param_type_not_indeterminate` end to end through the daemon.

  **(s) MySQL/MariaDB isolation/readonly `BEGIN` is a SINGLE-STATEMENT BATCH, and that is load-bearing (M1-S8a Task 8).** `actor::compose_begin_sql` is now dialect-aware (`compose_begin_sql(dialect, isolation, readonly)`, fed from `Pool::backend().dialect()` at the one call site in `begin_on_pool`). On MySQL 8.4 and MariaDB 11.8 `BEGIN READ ONLY`, `BEGIN ISOLATION LEVEL …` and `START TRANSACTION ISOLATION LEVEL …` are ALL `ERROR 1064 (42000)` (measured), so the composed form is `START TRANSACTION [READ ONLY]`, prefixed for the isolation cases with `SET TRANSACTION ISOLATION LEVEL …;` **in the same statement string**. Two reasons it is one string and not two calls: `Checkout::begin_tx_with` issues exactly ONE `simple_query` and wraps it in the whole pin/RFQ/tracker/Rule-A sequence (a second call would re-run all of it); and — the measured one — a **STANDALONE** `SET TRANSACTION …` returns an OK packet with `SERVER_SESSION_STATE_CHANGED` and **no trackers**, which `tracker::is_mutation` reads as a genuine session mutation, so every isolation/readonly transaction would taint into a full `COM_RESET_CONNECTION` at the next recycle. **BATCHED** (over the already-negotiated `CLIENT_MULTI_STATEMENTS`), `query_drop` drains both result sets and the FINAL OK packet carries a `TransactionState` tracker, which gates the bare-flag path off: no taint, `tx_status` reads `InTx`, and `SERVER_STATUS_IN_TRANS_READONLY` confirms read-only took. The batch consequently MASKS the intermediate statement's own trackers — acceptable **only** because the engine composes this string itself; a user batch still goes through the unchanged `Checkout::exec`, and the engine-composed BEGIN never passes through the M1-S8a Task 7 tx-control/lone-statement guard at all (`begin_tx_with` drives the RAW `PoolBackend::simple_query`). It is also one of the three concrete holes any future tracker-clean hygiene skip (§7.2, R2) must reconcile. **The `SESSION` form is FORBIDDEN, and the prohibition is load-bearing:** `SET SESSION TRANSACTION ISOLATION LEVEL …` would persist the level on the pooled connection past `COMMIT`, so the next tenant would inherit it — a cross-tenant connection-state leak (charter rule 6). The next-transaction-only spelling is correct *because* it does not persist, and the observable consequence is that **the level is NOT visible in `@@transaction_isolation`** (which keeps reporting the session default, rendered by MySQL with a hyphen: `REPEATABLE-READ`). Anyone verifying this behaviour must therefore prove it by a **lock conflict** — under `SERIALIZABLE` InnoDB converts a plain in-transaction `SELECT` into a locking read, so a concurrent `UPDATE` of that row blocks, while under the default `REPEATABLE READ` it does not — never by reading the variable back. That trap is real: the naive variable assertion is false, and its natural "repair" is the leak. The PostgreSQL strings are byte-identical to M1-S6's (all 8 still pinned verbatim), and `Dialect::Sqlite` is an explicit LOUD refusal rather than a silent PG fallback; the `match` over `Dialect` has **no `_` arm**, so a fourth dialect breaks the build (proven by adding one: `E0004` at `compose_begin_sql`). **PHP-reachable NAMED isolation constants are explicitly NOT in S8a**: they would need a new `[isolation]` section in the `/proto` registry (touching `registry.rs`'s `MethodsToml` and `Registry` **and** `build.rs`'s own `deny_unknown_fields` `Registry`), and Doctrine does not need them — `Connection::setTransactionIsolation()` emits `SET SESSION TRANSACTION ISOLATION LEVEL …` as plain SQL, not a driver flag.

  **Where the cross-tenant-leak guard lives, and where it deliberately does NOT (measured, not assumed).** A "the next tenant did not inherit the level" assertion at the POOL level is a guard that **cannot fail**, on both engine families: with the composer mutated to emit the forbidden `SET SESSION TRANSACTION ISOLATION LEVEL …` (MySQL) and `SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL …` (PG), the e2e assertions stayed GREEN — MySQL's `clean_reset_profile() = Some(Full)` runs `COM_RESET_CONNECTION` at every recycle and PG's targeted profile runs `RESET ALL`, so hygiene wipes the leak before any later tenant can observe it. Both such assertions were therefore DELETED rather than shipped as dead guards, with the measurement recorded in-source at both sites. The falsifiable leak guard lives one layer down, on a RAW backend connection with no hygiene in the way: `ferro-backend-mysql`'s `begin_dialect_it::the_batched_isolation_never_survives_the_transaction`, which reads the session level BEFORE the batch and again after `COMMIT` and after `ROLLBACK`, and goes RED (`SERIALIZABLE` vs `REPEATABLE-READ`) under exactly that mutation. Hygiene masking the leak is defence in depth, not the property being asserted.

  **A cancelled contending write is NOT a raw `57014` on the wire, and the lock-conflict proof asserts the §19.3 cell instead.** The concurrent `UPDATE` that proves `SERIALIZABLE` took is an autocommit WRITE bounded by `timeout_ms`, and the S4 fate matrix deliberately re-labels a cancelled/timed-out dispatched write as `WriteUnconfirmed{Indeterminate}` (`fate.rs`'s `is_57014` override), replacing the raw SQLSTATE with the engine's own payload — so `sqlstate` is `None` there by construction and the gate asserts `errc::WRITE_UNCONFIRMED` + `branch::INDETERMINATE` + the cancel message (which separates it from the other producer of that code, a `ConnectionLost` on a sent write).
