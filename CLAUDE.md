S9a is the slice that closed them, in 12 tasks under one plan, with **no `/proto` change** and no PHP change: every answer it mints reuses an existing code with its registry-pinned branch, and the two codes it wanted (`TX_PARTIALLY_COMMITTED`, `ERR_OVERLOADED`/`ERR_SHUTTING_DOWN`) are recorded as deferred candidates rather than hand-rolled (charter rule 2). SPEC §5.2, §7, §7.1, §7.7, §9.2, §12, §18, §19.3, §20.3 and §22.2 (ai)–(an) now say all of this. Two of the findings change what a drop-in user sees, and they pull in opposite directions.

**The blocker: `fate.rs` licensed replay of writes that had already persisted.** Every in-transaction statement loss classified `Retryable` on the premise "the transaction can never commit, so replay is safe" — and **on MySQL/MariaDB that premise is false**, because an implicit-commit statement (DDL, `LOCK TABLES`, `SET autocommit`, `CALL`, …) inside an explicit transaction commits everything before it. Measured live: `START TRANSACTION; INSERT 1; CREATE TABLE; INSERT 2;` then an abrupt disconnect with no COMMIT — **both rows persisted**. The concrete victim is Doctrine Migrations on MySQL, where transactional migrations are the default: BEGIN → INSERT the migration-log row → `ALTER TABLE` (the INSERT persists) → a later failure → `Retryable` → the framework replays → the log row double-applies. **The guard was built and merged FIRST** — because the same review measured that the field carrying the in-transaction fate (`in_tx: true`) was **unobservable by the entire suite**: flipped to `false`, eight live suites and 142 lib tests stayed green, the project's dominant defect class landed on its defining safety property. `in_tx_fate_it.rs` creates the missing event (a backend LINK death during an in-transaction statement, over the wire path) on PG 17, MySQL 8.4 and MariaDB 11.8; under the same mutation all three now go RED, re-measured at the doc pass rather than cited. The fix tracks `tx_writes_persisted` from the protocol authority (`tx_open()` false after a clean completion) plus a new **pre-dispatch lexical assist** (`ferro_classify::implicit_commit_hazard`, MySQL-family only, unknown-keyword → HAZARD) for the case no protocol signal can ever report, since MySQL commits BEFORE the statement executes. **Once set, the `Retryable` BRANCH is unmintable for that transaction** — branch-shaped, not errc-shaped, because a retryable `Sql` passthrough (a 1213 on the post-DDL statement) licenses the same replay a `TxDeadline` or a `ConnectionLost` does — and it reaches every in-transaction exit including the deadline reply and the **tombstone**. **Drop-in consequence:** on MySQL/MariaDB, after an implicitly-committing statement every later failure in that transaction reports `WRITE_UNCONFIRMED{Indeterminate}`, so a retry-the-closure wrapper correctly stops retrying it. PostgreSQL is byte-identical. One measured correction to the plan came out of execution: **`EXECUTE` is a hazard while `PREPARE`/`DEALLOCATE` are not** — the commit belongs to the statement that RUNS — verified live on both engines and again at the doc pass.

**The false alarm, in the other direction:** a statement on a connection that died BEFORE dispatch was reported `Indeterminate`, reproduced live on PG with the write provably unapplied. `PoolError::ConnectionLost` now carries the dispatch phase (struct-shaped, so every construction site had to CHOOSE at compile time), `Indeterminate` requires **sent AND dispatched**, and the safe default everywhere the phase is unattributable is *dispatched* — a wrong "yes" cries wolf, a wrong "no" licenses replay. MySQL phase attribution was closed rather than deferred, measured live on both engines with an in-flight CONTROL beside each. **This also answers M1-S8b's unreproduced pre-`HEAD` `Indeterminate` sighting**: yes, a terminal produced before the first row CAN reach the `sent` arm (the stream OPEN pre-builds it), and that cell is now `Retryable` — but the observation itself captured no message text and never reproduced, so §21 open item 1 records an answered question over an unclosed observation, and open item 2 (the 1-in-12 flake) is untouched.

**Three unbounded awaits, one shape, each leaking a pool permit** — and only S8a's version probe had ever been bounded, because that review caught it. `checkout_timeout` now bounds the WHOLE checkout (acquire + recycle cleanup + dial) instead of the semaphore acquire alone: `max_size` wedged dials used to take a pool to **zero usable capacity permanently, even after the backend recovered**, while the module docs claimed otherwise. The reaper's `ping()` is bounded by the same knob and **evicts** on expiry (a dropped ping future leaves unknown protocol state; recycling it would trade a wedged reaper for a cross-tenant leak). The post-cancel drain on both buffered EXEC paths is bounded by `CANCEL_DRAIN_BUDGET = 5 s` — that one was **charter rule 4 broken, not merely a hang**, since the request received no terminal at all — and an expiry taints the connection unconditionally, on the tx path explicitly rather than trusting teardown's ROLLBACK to fail. Deliberate, stated cost: a recycle cleanup no longer gets a fresh full budget per popped connection, so a checkout whose budget it consumes ends `POOL_TIMEOUT{Retryable}` instead of silently spending a second one. Poisoned idle mutexes now recover instead of aborting the process from `Checkout::drop` during unwind.

**Availability and shutdown.** The codec reserved up to 16 MiB the instant a HEADER arrived; it now reserves at most one 64 KiB step ahead of the bytes actually received, so an attacker pays for what they pin. Three knobs landed: `max_connections` (default **512**, an fd budget under systemd's 1024 `DefaultLimitNOFILE`, not a round number), `frame_read_timeout` (30 s) and `idle_timeout` (**disabled by default** — the sync PHP client cannot ping while blocked between requests, so a nonzero default would sever every quiet FPM worker). `frame_read_timeout` is implemented as a **STALL detector, not the per-frame completion deadline the plan specified**: a completion deadline severs healthy-but-slow clients exactly when the host is loaded, measured under mutation as `EPIPE` under a client still sending. And **`SIGTERM`'s drain now reaches sessions, pools and transaction actors** instead of only stopping `accept()`: new checkout-acquiring work is refused with a real terminal, pinned transactions keep running for the window, and each session exits through its own cleanup. **`drain_deadline` therefore CHANGED MEANING** — it is the window existing work gets, with a 3 s grace before the hard backstop, so a unit's `TimeoutStopSec` must be sized against the SUM (§18).

**Recorded, not closed** (each named in §22.2 rather than buried): the STREAMING abort path still awaits its drain unbounded — the same charter-rule-4 shape (ak) closed for the buffered paths, left to a plan entry because it touches the measured-sound ordering machinery; the implicit-commit hazard cries wolf for an in-transaction statement that errored WITHOUT running (safe direction, and the alternative is the inference this project refuses); the accept loop hot-retries under `EMFILE`; and a drain-deadline terminal for an in-flight tx statement is `PROTOCOL{NonRetryable}` where `TxDeadline{Retryable}` would be more informative (a pre-existing teardown-ordering race, safe either way — and reading it against §22.2's M1-S4 entry surfaced the one **mutual contradiction** this doc pass had to repair, since that entry records the opposite arm winning; both are true of different instants and the earlier entry is corrected in place). **Process worth carrying:** every guard added was mutation-proven with the RED output journalled, and doing that found real defects **in the plan** — two named mutations came back GREEN (i.e. named a guard that could not fail), several plan test bodies would not compile or could not pass against a CORRECT implementation, and one stated hazard was simply false. Implementers reported those rather than working around them, which is the whole point; and it is not new — S5's and S6's plans were falsified pre-build too, and S8b's review found 6 blockers in a slice where every gate was green. Gates at the boundary: **855 Rust tests live / 0 failed** against PG 17 + MySQL 8.4 + MariaDB 11.8 (789 before), `cargo fmt` + `clippy -D warnings` clean, no-skip gate green, no PHP or `/proto` change.

Next up: **M1-S9 — the M1 exit gate**, and S9a changed what it inherits. What remains is short on code and long on things nobody has done yet. **The bar itself has to be renegotiated first, not just met:** §17 still says "DBAL 4 suite green" while §14 already says something else, and "green" is a word this project has proved can be meaningless — the replacement is the form S8c actually built, a baseline exact-match plus a triage table in which the category "an engine gap this run measured and did not close" is EMPTY. Then: (1) **the Doctrine ORM functional suite has NEVER been run** — not once, on any backend — and §14's bar names it; (2) **SQLite is impossible** (no backend exists), so a third of §14's stated bar is unreachable and must be formally removed rather than quietly dropped; (3) the residual PG/MySQL non-passing tests, all already triaged as a documented Ferro semantic or an upstream assumption we structurally cannot satisfy — closing any of them is a decision, not a bug fix; (4) **§20.3's kill-`ferrod` fate-correctness harness has never been built** — it is the acceptance test for the property the whole design exists to protect, and S9a's live chaos is all backend-link chaos, where the daemon survives. Then the genuinely open engineering: `affected` on the stream terminal (a `/proto` change that would let the prepared path stream and close the last gap in §14's never-buffer clause), MySQL/MariaDB `query_stream` (§22.2 (n)), a `/proto` `TxNotFound` code so `rollBack()` need not swallow `ERR_PROTOCOL`, the tracker-clean hygiene `None`-skip (R2), chunked `LARGE_OBJECT` bind, savepoint verbs in the assist-lexer safe-list, and the Laravel tier. **S9a's own four residuals carry forward** and are named in §22.2 (ai)/(ak)/(al)/(am): the streaming abort path's unbounded drain (the last known charter-rule-4 hole), the implicit-commit hazard's cry-wolf on a statement that errored without running, the accept loop's hot retry under `EMFILE`, and the drain-deadline terminal that reports `PROTOCOL` where `TxDeadline` would inform better. **Of the two open items filed UNREPRODUCED at S8b, one is now half-closed:** the pre-`HEAD` `Indeterminate` sighting's fate QUESTION is answered and a sufficient mechanism is fixed (§19.3), but the observation still captured no message text and never reproduced, so it stays open as an observation; the 1-in-12 flake in the same test is untouched. **Beyond M1, the M0 review's roadmap findings are unaddressed and are not S9's to smuggle in:** upstream TLS does not exist and is in no bar, D12 is exiting M1 unadjudicated with its one provisional measurement pointing the wrong way, the vendored forks' real exposure is CVE-lag (four unfiled `tokio-postgres` accessors plus a `mysql_async` fork), §17's M2–M5 predate everything M1 learned, and D7 (naming/trademark) was a "before M1" task that M1 is about to exit without. **The standing caveat has moved rather than gone.** It used to be that the M0 core had never had a whole-branch adversarial pass; it has now had one, and it produced a data-corruption blocker. What has not had one is **M1-S9a itself** — twelve tasks that changed the fate matrix, the pool and the session layer, held to per-task mutation discipline but never read whole-branch by a second model. Every slice that has had such a pass produced confirmed defects, including the ones where everything was green.

## What Ferro is

A **per-host database access engine for PHP**. One Rust daemon (`ferrod`, tokio) owns all upstream DB connections, pools them in transaction mode, and multiplexes many PHP-FPM workers over a local Unix socket — while remaining a **drop-in** replacement for Doctrine DBAL and Laravel Eloquent (config-only adoption).

It is deliberately **not**: a database, a SQL rewriter, a result cache, or an ORM-in-Rust. The engine's job ends where live PHP object semantics begin. See Ground rule 6 and SPEC §3.

## Architecture at a glance

The whole design lives in the spec; this is the map, with section pointers so you read the 2–3 relevant sections, not all 47 KB.

```
PHP-FPM workers (N)  ── one UDS conn each, all requests multiplexed ──┐
  ferro/client         native typed API, Fibers-aware   §10, §10.1   │
  ferro/doctrine-dbal  DBAL Driver SPI → client          §14         │
  ferro/laravel        Illuminate Connection → client    §15         │
        │  UDS /run/ferro/{schema_hash}.sock  (TCP fallback FERRO_ADDR)
        ▼
  ferrod (Rust/tokio)                                                │
   session layer   handshake+epoch, auth, multiplexing, PING/PONG  §5
   SQL service     EXEC: param bind, result framing                §6
   TX service      tx_id pinning, savepoints, deadlines            §6, §7
   pin engine      protocol signals first, assist lexer second     §7.1–7.2
   pools           pg | mysql | sqlite | mssql (+ replicas)        §7, §8
   manifest store  query_id → plan (checked SQL / codegen)         §11
   admin/metrics   OTLP, Prometheus, slow log                      §13
```

Load-bearing ideas that shape almost every change (all enshrined in the charter's Ground rules):

- **Transactions pin to a `tx_id`, not to the client socket** (§4, §7). This is what makes Fiber-suspended requests and multiplexing correct.
- **Every in-flight request ends in exactly one `END` frame** (§5.2). All session state machines key off this.
- **The `Indeterminate` error branch** (§9.2, §19.3) — a write whose fate is unknown — is the spec's defining safety property. The engine *never* transparently retries; it classifies and reports, and retry is client policy. Auto-retry of an indeterminate write is licensed *only* by a manifest `idempotent: true`.
- **`boot_epoch`** (§5, §19.1): a changed epoch on reconnect voids all engine-side state; the client resilience loop is built around it.
- **`/proto` is the single source of truth** for method ids, flags, error codes, type tags (§20.2). Hand-written protocol constants in Rust or PHP are a defect.

# Charter (the working agreement)

## Ground rules

1. **Decisions in SPEC §21 are binding.** Do not re-litigate them in code, comments, or refactors. If one proves impossible, stop and raise it — don't route around it.
2. **`/proto` is the single source of truth** for method ids, flags, error codes, and type tags. Any protocol change updates the registry, the golden vectors, and both codecs (Rust + PHP) in the same change set. Hand-written protocol constants anywhere are a defect.
3. **The engine never transparently retries user statements** (SPEC §3, §19.3). It classifies and reports; retry is client policy. This is load-bearing for the `Indeterminate` guarantee — do not "helpfully" add engine retries.
4. **Every in-flight request terminates in exactly one END frame.** All session-layer code is written against that invariant.
5. **Correctness over throughput until the M0 gate.** Optimize only against recorded bench numbers (SPEC §16.1), never speculatively.
6. **Scope discipline:** no ORM semantics in Rust, no SQL rewriting, no result caching, no read/write inference (SPEC §3). The drop-in tiers change execution, never SQL generation — Grammar/Processor and DBAL platforms stay stock.
7. **PHP client stays dependency-free at runtime.** Optional extensions (`ext-msgpack`, `ext-sockets`) are runtime-detected, never required.

## Build order

Follow SPEC §17 milestones; within M0, execute §17.1 tasks in order. M0 does not exit until the D12 bench measurement is recorded in `bench/results/` with its environment manifest.

## Definition of done (every task)

- Tests: unit + (where applicable) integration against `/testkit` backends; protocol work adds/updates golden vectors; pin-engine work adds a pin-cause assertion; §19 work extends the chaos harness.
- Gates green: `cargo fmt --check`, `cargo clippy --workspace -- -D warnings`, `cargo test --workspace`, PHPUnit, PHPStan level 9 on `php/client`.
- The relevant SPEC section still tells the truth. If implementation forced a deviation, amend the spec text and add a line to §22 in the same change.
