# Doctrine ORM 3 functional suite vs Ferro — recorded results, **M1-S9** (first run ever)

**Date:** 2026-08-13 · **Slice:** M1-S9 (the M1 exit gate) · **Runner:** `testkit/orm-suite.sh`

The Doctrine ORM functional suite had **never been run against Ferro on any backend**. SPEC §14
names it in the M1 exit bar, so this file is the first measurement — recorded under the bar M1-S9
renegotiated: a **stock `pdo_*` comparator**, a **two-run exact match** of both the result line and
the ordered non-passing set, and a **five-category triage in which category (a) — a driver defect —
must be EMPTY**.

**This is a measurement bar, not a green bar, and the word "green" is not used below.** It cannot
be: the driver we replace is not green either — stock `pdo_mysql` fails 4 of 3485 tests on MySQL
8.4.11, and those same 4 fail byte-identically through Ferro.

**Ferro against stock, stated plainly:**

- **PostgreSQL: 50 fewer tests pass** — 47 that error, plus 3 that upstream skips itself under the
  configuration Ferro requires (see *What this run does not cover*). Stock passes everything.
- **MySQL: 6 fewer.** Ferro's non-passing set is stock's 4 **plus** 6. The 4 are byte-identical
  through both drivers (proved below), so **6 tests are Ferro-attributable**.
- **MariaDB: 6 fewer.** The same 6 tests, the same cause. Stock MariaDB is itself clean here —
  **the 4 MySQL failures do NOT reproduce on MariaDB**, because `MariaDB110700Platform` (not
  `MySQL84Platform`) generates that DDL. The comparator is therefore not uniform across the MySQL
  family, and every "byte-identical to stock" claim in this file is made per backend, never per
  family.

**Category (a) — a driver defect — is EMPTY on all three backends.** That is a measured claim, not
an assumption: each cluster below was reproduced or controlled for independently, and the one
category-(a) defect this suite did find (`fetchFirstColumn` truncating at a boolean `false`) was
fixed in `d436f83` **before** these numbers were recorded. Its ORM witness,
`GH9230Test::testIssue with data set "bool=false"`, is absent from the PG non-passing set while the
three `float=` data sets of the same test remain — so the fix is visible from the ORM vantage, not
merely from its own unit test.

**Category (e) — an engine gap this run measured and did not close — is NOT empty on PostgreSQL:
10 tests.** Under the renegotiated bar (e) rows do not block M1 exit, but each carries a filed
follow-up with an explicit milestone assignment. That is a decision recorded here, not a gap
hidden.

## The comparator is honest, and it is NOT identically configured

The stock leg runs upstream's own configuration. The Ferro leg additionally applies the **one
documented adoption setting Ferro's own docs require on PostgreSQL**: D-S8b-5's SEQUENCE identity
preference. Read as "same configuration, two drivers" the pair would be wrong; read as *"what stock
Doctrine does here"* vs *"what Ferro does under the configuration its documentation requires"* it is
the honest comparison, and it is the one this file makes.

The measured cost of omitting that setting is the reason it is applied rather than argued about:
**1229 errors, about 35 % of the suite** (research-orm step 6b) — and every one of them carries the
D-S8b-5 error text, i.e. an unconfigured run reads as a genuine finding about PostgreSQL identity
strategy rather than as a misconfigured harness.

## The harness interventions, NAMED

**This is upstream's suite under a REPLACED test harness and the documented configuration.** Four
interventions, each of which changes what the number means and none of which touches
`tests/Tests/ORM/**` (the tests themselves are restored to the pinned tag on every invocation, and
the runner refuses to continue if that restore leaves any drift):

1. **`tests/Tests/TestUtil.php` is REPLACED** (`testkit/orm/TestUtil.ferro.php`). Upstream's
   `mapConnectionParameters()` maps only `driver` and silently discards `driverClass`; setting
   `db_driverClass` alone throws, and setting both makes `db_driver` win — which runs **stock PDO
   under a Ferro-labeled banner**. The replacement honours `db_driverClass`, keeps a stock
   comparator branch, and is grep-verified after it is copied.
2. **ONE line in `tests/Tests/DbalExtensions/Connection.php`** on the Ferro leg: the parent import
   changes from `Doctrine\DBAL\Connection` to `Ferro\DBAL\Wrapper\FerroConnection`. Upstream
   hardcodes that class as the suite's `wrapperClass` and `OrmFunctionalTestCase`'s query-count
   assertions depend on it, while Ferro's `wrapperClass` is REQUIRED (§22.2 (ah)) — one slot, two
   claimants. Without the re-parent, `transactional()` masks `IndeterminateWriteException`.
   `FerroConnection` declares no constructor, so the QueryLog wiring is inherited unchanged.
3. **The D-S8b-5 SEQUENCE identity preference, PostgreSQL + Ferro only**
   (`setIdentityGenerationPreferences([PostgreSQLPlatform::class => GENERATOR_TYPE_SEQUENCE])`,
   hooked in `configureProxies()`). Cost of omitting it: **1229 errors**, above. The bootstrap
   ASSERTS the preference actually reached the ORM `Configuration` before any test runs — upstream's
   `configureProxies()` early-returns on PHP ≥ 8.4 with native lazy objects, so a preference written
   after that line is dead code, and the failure would not have been loud.
4. **A fail-closed, container-side database reset before every recorded run**, into a dedicated
   `doctrine_orm_tests` database — never the shared `ferro` one. A non-zero reset aborts the run.

**The contact assertion is what makes the banner mean something.** Before the first test, the
bootstrap asks the connection what it *is*: the Ferro leg refuses to run unless
`getNativeConnection()` is a `Ferro\Client\Connection` **and** the suite's own
`DbalExtensions\Connection` is a subclass of `FerroConnection`; the stock leg asserts the dual (a
`PDO`, and not a Ferro connection). Both directions of the same lie are closed. This project has
already published a green acceptance line produced with **zero engine contact** (§22.2 (z)).

## Reproducibility — THREE runs per leg, not two

Reproducibility is the deliverable, not the number. M1-S8b's DBAL acceptance number was
non-reproducible (23 then 33 errors on identical commands) until its reset was fixed, and the ORM
research probe hit a worse accident: an unreset run turned 48 non-passing into **227**, *with a

the identical **ordered** non-passing set (the ordered set carries the ` with data set "…"` suffix,
so a provider-level change cannot hide inside a matching count). A **third** run of every leg was

The comparison is mechanical, not visual: the runner extracts the non-passing set from the JUnit XML
(never from PHPUnit's human output, whose `N) Class::method` blocks are also produced for skipped
tests in some verbosity modes — a text scan is exactly the species of guard this repository keeps
having to delete), diffs it against `docs/orm-suite/baseline/`, and makes its **exit status** mean
"does this match what we recorded". Drift is reported in BOTH directions: `-` lines now pass, `+`
lines are newly non-passing.

A run carrying any narrowing argument (`--filter`, `--group`, a bare path) or `--no-reset` announces
`recordable: NO` and is refused a baseline comparison or update. No number in this file comes from
such a run.

### Recording discipline: one defect in the runner, found and fixed while recording

The runner protected the *contract* (the committed baseline) from a debug run but not the
*evidence*. `--log-junit` wrote to a fixed path per `(mode, backend)` regardless of recordability, so
a `--filter` diagnostic silently replaced a 3485-test recorded run's JUnit file with a 6-test one —
measured, while triaging this very document — even as the baseline gate correctly reported "not
compared". The JUnit file is the half of a recorded run that a reader **cannot** re-derive from the
committed baseline: every triage cluster below comes from it.

Fixed here: a non-recordable run now writes `junit-<mode>-<svc>.debug.xml`. Proven by re-running the
exact diagnostic that caused the damage — the recorded file came back byte-identical under
`md5sum -c` and the 6-test result landed in the `.debug.xml`. All six recorded JUnit files were then
regenerated by full recordable runs (run 3 above).

### PostgreSQL — 47

**(b) Sub-second `TIMESTAMPTZ` read refusal — 16 tests.** Every one fails with the driver's own
message: *"the TIMESTAMPTZ value '2026-08-18T07:50:04.684132Z' cannot be handed to Doctrine's type
layer — Doctrine's `DateTimeTzType` parses only whole seconds on every platform and has no fallback,
so the sub-second part could only be dropped … It is refused rather than converted because
Doctrine's stock converters would accept it SILENTLY and produce a different value."* This is
§22.2 (ab) rule 2 — *we refuse what PDO corrupts* — working as designed. Relaxing it is a POLICY
decision with a filed follow-up, not a bug fix.

- `QueryDqlFunctionTest::testDateAdd` — data sets `year`, `month`, `week`, `day`, `hour`, `minute`, `second` (7)
- `QueryDqlFunctionTest::testDateSub` — the same 7 data sets
- `QueryDqlFunctionTest::testDateAddWithColumnInterval`, `::testDateSubWithColumnInterval`

**(b) D-S8b-5 — `lastInsertId()` is not emulated on PostgreSQL — 10 tests.** All fail with *"Ferro:
PostgreSQL reports no generated key on the wire, and Ferro will not emulate lastInsertId() with a
follow-up query — on a transaction-mode pool that runs on a different connection and returns a wrong
key."* The suite-wide SEQUENCE preference does not reach them because **their fixtures hard-code
`#[GeneratedValue(strategy: 'IDENTITY')]`** (verified in the fixture sources, e.g.
`tests/Tests/Models/ReadonlyProperties/{Author,Book,SimpleBook}.php`,
`GH11341Test`, `GH5562Test`, `DDC2106Test`, `tests/Tests/Models/DDC3597/DDC3597Root.php`), which
overrides a per-platform preference. Only patching upstream fixtures could close them, and that
would change the claim this file makes. D-S8b-5 is binding (charter rule 1).

- `ReadonlyPropertiesTest::testSimpleEntity`, `::testEntityWithLazyManyToOne`,
  `::testEntityWithEagerManyToOne`, `::testEntityWithManyToMany` (4)
- `Ticket\DDC2106Test::testDetachedEntityAsId`, `Ticket\DDC3597Test::testSaveImageEntity` (2)
- `Ticket\GH11341Test::testInstanceOf` data sets `#0`, `#1`, `#2` (3)
- `Ticket\GH5562Test::testCacheShouldBeUpdatedWhenAssociationChanges` (1)

**(b) Multi-table DQL temp tables — 6 tests, the §7.4 transaction-mode semantic.** All fail with
`table "company_persons_id_tmp" does not exist`. `MultiTableDeleteExecutor::execute()` (and its
UPDATE twin) issues `CREATE TEMPORARY TABLE`, then the INSERT/DELETE/DROP as **separate
`executeStatement()` calls with no transaction around them** — verified in the ORM source. On a
transaction-mode pool each autocommit statement may land on a different backend connection, so the
temp table is invisible to the next statement. This is identical to what pgbouncer's transaction
mode does to the same code.

MEASURED both directions through `ferro/client`, so the mechanism and the workaround are facts, not
inference:

```
-- autocommit (what MultiTableDeleteExecutor does today)
   autocommit: Ferro\Client\Error\NonRetryableException: relation "probe_tmp_899207" does not exist
               (code=12289, branch=3, sqlstate=42P01)
-- the SAME statements inside one explicit transaction (the documented workaround)
   in-tx: OK, rows={"cols":["id"],"rows":[[1]],"affected":1,"last_insert_id":null}
```

- `AdvancedDqlQueryTest::testUpdateAs`, `::testDeleteAs`
- `ClassTableInheritanceTest::testCRUD`, `::testBulkUpdateIssueDDC368`, `::testBulkUpdateNonScalarParameterDDC1341`
- `Ticket\DDC2090Test::testIssue`

**(c) `DDC832Test` orphan-sequence collateral — 5 tests.** They fail with
`relation "INDEX" does not exist` / `relation "LIKE" does not exist` — i.e. the schema was never
created, not a query defect. Cause, established by control rather than by reading: the class's
`tearDown()` drops its tables and then drops the identity sequences **only under a
`method_exists($platform, 'getIdentitySequenceName')` gate that is DBAL 3 only**; under DBAL 4 the
sequences survive, the next `setUp()`'s `createSchema` fails on `CREATE SEQUENCE … already exists`,
and upstream's `createSchemaForModels()` **swallows `ToolsException` silently**
(`OrmFunctionalTestCase.php:490-496`) — so the tables are simply absent for tests 2..6 of the class.

The control makes it an upstream assumption rather than a Ferro behaviour:

| leg | result | sequences left in `doctrine_orm_tests` after the class |
|---|---|---|
| stock/pg (upstream default IDENTITY) | `OK (6 tests, 6 assertions)` | none |
| Ferro/pg (D-S8b-5 SEQUENCE) | `Tests: 6, Errors: 5` | `INDEX_id_seq`, `LIKE_id_seq` |

Upstream's cleanup assumes the stock IDENTITY default; Ferro-on-PG cannot use it (D-S8b-5).

- `Ticket\DDC832Test::testQuotedTableBasicRemove`, `::testQuotedTableJoinedUpdate`,
  `::testQuotedTableJoinedRemove`, `::testQuotedTableJoinedChildUpdate`,
  `::testQuotedTableJoinedChildRemove`

## What this run does NOT cover

Stated so nobody reads "3485 tests" as parity:

1. **Two upstream groups are excluded**, matching upstream's own CI: `performance` and
   `locking_functional`. The 3485-test denominator is defined by those exclusions.
2. **The second-level-cache job is not run.** Upstream runs it as a separate CI job with a different
   configuration; this harness does not.
3. **Three tests RUN on stock PostgreSQL and are SKIPPED on Ferro PostgreSQL** —
   `Ticket\DDC3634Test::testSavesIntegerAutoGeneratedValue`,
   `::testSavesIntegerAutoGeneratedValueWithJoinedInheritance`,
   `::testSavesVeryLargeIntegerAutoGeneratedValue`. The skip is UPSTREAM'S OWN guard, captured
   verbatim: *"Need a post-insert ID generator in order to make this test work correctly"*
   (`DDC3634Test::setUp`, on `! $metadata->idGenerator->isPostInsertGenerator()`). It fires because
   the PG leg runs the SEQUENCE strategy, a pre-insert generator. Nothing in Ferro's execution layer
   skips them — but they are three `lastInsertId()`-shaped tests (the class installs a
   `LastInsertIdMocker` middleware) that the Ferro PostgreSQL column does not exercise, so the PG
   gap against stock is **50 tests, not 47**. MySQL and MariaDB skip sets are identical between
   modes.
4. **Day-over-day reproducibility is untested** *for the comparator; PARTLY discharged for the
   Ferro legs after the fact.* All three runs of each leg recorded here were made in one session, on
   one host, against one set of containers. The M1-S9 **exit-gate** run (Task 7,
   `docs/followups/2026-08-13-m1-exit-maintainer-items.md`) then re-executed the three **Ferro**
   legs twice each on 2026-09-08 — 21 days after this document's recording commit `3bd026e`
   (2026-08-18), in a different session and after the testkit containers had been stopped and
   restarted (same containers, same image digests as the manifest above) — and reproduced every
   result line and every ordered non-passing set exactly. The **stock comparator** legs were not
   re-run, so the comparator columns remain single-session.
5. **Streaming is not exercised as streaming on the MySQL family** — `fetch:stream` returns a clean
   `Unsupported` there (§22.2 (n)) and the driver buffers; the ORM suite issues no statement that
   would distinguish the two.
6. **§14's bar names PostgreSQL + MySQL. MariaDB is recorded here additionally**, on the same
   discipline, because the runner and the reset support it and a first measurement is cheaper to
   take than to argue about.

## How to reproduce

```bash
# the recorded numbers — run each leg twice; the second run must print `baseline: MATCHES` and exit 0
for svc in pg mysql mariadb; do
  for mode in stock ferro; do
    FERRO_ORM_SVC=$svc FERRO_ORM_MODE=$mode ./testkit/orm-suite.sh > /tmp/orm-$mode-$svc.log 2>&1
    echo "$mode/$svc EXIT=$?"          # NOT `| tee` — a pipeline's status is tee's, and a failed
  done                                  # run would be recorded silently at the moment of recording
done

# to re-record after an intended change (and only then)
FERRO_ORM_BASELINE=update FERRO_ORM_SVC=pg FERRO_ORM_MODE=ferro ./testkit/orm-suite.sh
```

The committed baselines are `docs/orm-suite/baseline/{pg,mysql,mariadb}.txt` (Ferro) and
`docs/orm-suite/baseline/stock-{pg,mysql,mariadb}.txt` (the comparator). A `stock-*.txt` that is
empty is a recorded fact — "stock has no failures on this backend" — not a missing file.
