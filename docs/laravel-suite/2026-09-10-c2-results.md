# M2 / C2 — the Illuminate integration suite

**Date:** 2026-09-10. **Runner:** `testkit/laravel-suite.sh`.
**Upstream:** `laravel/framework` **v11.51.0** (pinned clone), `orchestra/testbench-core ^9.0`.
**Backend:** PostgreSQL 16.13, one `ferrod` per run, `laravel_tests` database, reset before every
run.
**Scope:** all **89** driver-agnostic top-level files of `tests/Integration/Database/`
(`testkit/laravel/allowlist.txt`), **633 test cases** — plus the PostgreSQL-specific subdirectory as
a separate column (`testkit/laravel/allowlist-postgres.txt`, 76 cases).

## The control column, and why it exists

`FERRO_LARAVEL_DRIVER=stock-pgsql` runs the identical tests against the identical server through
upstream's own `pdo_pgsql`. It answers the one question a 633-test triage keeps asking — *is this
non-pass ours, or this framework/server pair's?* — and it earned its place before it was built: two
`SchemaBuilderSchemaNameTest` cases looked like a Ferro schema gap, and the control reproduced them
exactly.

It cannot be reached by accident and cannot silently degrade:

- the value is explicit and never the default;
- `bootstrap.php`'s contact assertion **inverts** for it — under `stock-pgsql` it refuses to run if
  the resolved connection turns out to be a Ferro one, checked on the connection's actual class
  rather than on the env var being verified;
- **mutation-proven twice.** Registering Ferro's resolver for `pgsql` kills the run one step
  *earlier* (Ferro's own config refusal — the control array carries no `ferro_socket`); adding that
  socket so a real Ferro connection IS built is what makes the inverted check fire. Both refuse to
  run; neither reports a number;
- the CI lane re-checks it independently, grepping for `connection=Illuminate\Database\PostgresConnection`.

This is the ONE place PHP holds database credentials, which §12/D8 otherwise forbids. That is
inherent to being PDO, and the mode is measurement-only.

## Triage — every non-pass

### `pgsql` and the control: 2 errors, and they are upstream's own

`SchemaBuilderSchemaNameTest::testIndexes` and `::testAutoIncrementStartingValue`, **`with prefix`
data sets only**. The control fails them identically, so they are this framework/server pair's, not
Ferro's. Not investigated further for that reason.

### `ferro-pgsql`: 9 more, and all nine are the driver-NAME artifact

Positively identified from upstream source in each case — no inference:

| tests | how the name is read |
| --- | --- |
| 6 × `QueryBuilderTest::*WithInvalidOperator` | `if (in_array($this->driver, ['pgsql','sqlsrv'])) $this->expectException(PDOException::class);` — the expectation is never armed, so the exception the test asks for propagates as an error |
| 2 × `TimestampTypeTest::testChange*Column` | `match ($this->driver) { 'mysql','mariadb','pgsql' => 'timestamp', default => 'datetime' }` — the assertion compares against the wrong expected type |
| 1 × `SchemaBuilderTest::testModifyingColumnToAutoIncrementColumn` | `if (in_array($this->driver, ['pgsql','sqlsrv'])) $this->markTestSkipped(…)` — the test skips itself on PostgreSQL because the operation genuinely is not supported there, and under another name it runs and fails |

The same mechanism accounts for the skip difference (54 vs 26).

**This is the cost of §15's one-word config change, stated rather than smoothed over:** an
application that adopts Ferro under `ferro-pgsql` reports a driver the ecosystem does not recognise,
and third-party code that branches on `getDriverName()` takes its fallback path.
`FerroConnections::register(['pgsql' => 'ferro-pgsql'])` is the opt-in escape hatch, with the sharp
edge stated at its call site (it hijacks *every* `pgsql` connection in the application).

## `search_path` belongs on the pool DSN, and Laravel needs it in BOTH places

`SchemaBuilderSchemaNameTest` creates objects in `my_schema` and renames them by **unqualified**
name, which only resolves against the session `search_path`. A stock Laravel app sets `search_path`
in `config/database.php` and the PDO connector issues `SET search_path`; a Ferro app cannot, because
the session is **pooled** — so it belongs on the ferrod pool DSN, where libpq's
`options=-csearch_path=…` puts it. **Measured: without it those cases fail; with it they pass.**

And Laravel *also* needs the config key, because `PostgresBuilder::getSchemas()` reads `search_path`
from the **config array** and never asks the server. So a Ferro application using a non-default
schema sets it in both places. That is a documented configuration requirement, not an
incompatibility.

## The one Ferro gap the PostgreSQL-specific column found: `DB::escape()`

`Postgres/EscapeTest::testEscapeString` was the single failure in that directory, and the control
passed it — so a Ferro gap, not an environment one. `Connection::escapeString()` is
`getReadPdo()->quote($value)`, and `FerroPdoShim` refused `quote()` by name, on the sibling Doctrine
tier's reasoning: *implementing it means owning dialect-specific SQL escaping, security-critical
code with no known caller*. The caller turned out to exist and to be ordinary — beyond `DB::escape()`
itself, `Grammar::substituteBindingsIntoRawSql()` reaches it, which is every `Builder::toRawSql()`,
every `->dd()` on a query builder, and the SQL that query-log tooling renders.

It is implemented, and the security half of that sentence is why it looks the way it does:

- **Illuminate does the dangerous half first.** `Connection::escape()` rejects NUL bytes and invalid
  UTF-8 itself and routes null/int/float/bool/binary/array elsewhere, so what reaches `quote()` is a
  valid UTF-8 string with no NULs.
- **The rule is doubling `'` and nothing else**, which is complete only while
  `standard_conforming_strings` is `on` — so it is **verified, not assumed**, by one `SHOW` per
  connection, cached. Reading it from a pooled checkout is sound because a non-local `SET` taints
  the connection and hygiene restores the server default, so every checkout begins from the value
  the probe observed.
- **Measured against `pdo_pgsql` on PostgreSQL 16** over eight cases including `backslash-then-quote
  \'` and `quote-then-backslash '\`: byte-identical output, and every case round-trips through
  `SELECT <literal>` to the original bytes.
- **`PDO::PARAM_LOB` is refused**, not ignored — PostgreSQL's binary literal is `'\x…'::bytea`, a
  different shape, and Illuminate builds it in PHP via `escapeBinary()` without touching PDO.

Two mutations were run. Dropping the `'`-doubling turns 9 live cases red. **Dropping the
`standard_conforming_strings` verification was GREEN live** — every server this project runs against
has it `on`, so the check is unfalsifiable there; that is stated rather than left as an assumption,
and an offline test over a scripted session is where that mutation goes red.

## Two defects the widening itself found and fixed

Both in the harness rather than the product, and both were the "wall of errors with one cause"
shape: `Class "Faker\Factory" not found` (24 errors — a missing harness dev dependency), and 26
errors inside Ferro's own *correct* "a connection needs `ferro_socket`" refusal, because upstream
clones `database.connections.{$this->driver}` and the harness had named its connection something
else. The connection is now named after its driver, with **one** config array — two copies diverge
the moment a test mutates one, which is exactly what `SchemaBuilderSchemaNameTest` does to
`search_path`.

## What this is NOT

§15's acceptance bar is the Eloquent suite on PostgreSQL, **MySQL and SQLite**. MySQL is not run
(the tier registers `ferro-pgsql` only), SQLite is unreachable until the SQLite backend (C3) exists
at all, and 633 cases is the driver-agnostic slice of upstream's ~656 across 131 files — the
per-driver subdirectories are excluded on purpose (see the allowlist header). **The bar is not met.**

## Reproducing

```
docker compose -f testkit/docker-compose.yml up -d --wait pg
DSN='postgres://ferro:ferro@127.0.0.1:55432/laravel_tests?options=-csearch_path%3Dpublic,my_schema'
for drv in ferro-pgsql pgsql stock-pgsql; do
  FERRO_LARAVEL_DRIVER=$drv FERRO_LARAVEL_SVC=pg FERRO_LARAVEL_DSN="$DSN" bash testkit/laravel-suite.sh
done
```

The numbers above were produced on this container with system PostgreSQL 16.13 and
`FERRO_LARAVEL_SVC=psql` (a LOCAL `psql` running the identical `testkit/laravel/reset-pg.sql`). The
`laravel-suite` GitHub workflow runs all three columns twice each on a GH runner against the
containerised backend; re-record from its logs whenever the numbers change.
