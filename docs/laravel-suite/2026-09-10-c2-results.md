**Date:** 2026-09-10. **Runner:** `testkit/laravel-suite.sh`.
**Upstream:** `laravel/framework` **v11.51.0** (pinned clone), `orchestra/testbench-core ^9.0`.
**Backend:** PostgreSQL 16.13, one `ferrod` per run, `laravel_tests` database, reset before every
run.

Both columns are the same code against the same database; only the Illuminate `driver` NAME the

`FerroConnections::register()`'s `$aliases`). Every run's log carries the contact-assertion line and
the reset line; the lane refuses to count a run missing either, or one that did not run under the
driver name it claims.

**This is a CURATED SUBSET, not §15's bar.** `testkit/laravel/allowlist.txt` names five
driver-agnostic files out of upstream's `tests/Integration/Database` tree. §15's stated bar is the
Eloquent suite on PostgreSQL, MySQL and SQLite: **MySQL is not run** (the tier registers
`ferro-pgsql` and nothing else today), **SQLite is unreachable** until the SQLite backend (C3)
exists at all, and 71 tests is a fraction of upstream's ~656. Say that, rather than restating the
bar. "71 / 71" means the curated subset is clean; it does not mean the bar is met.

## Triage

### At C2b — 6 non-passes under `ferro-pgsql`, 0 under the alias

All six are the **driver-NAME artifact**, and there is no other category left.
`testWhereDateWithInvalidOperator` and its five siblings carry
`#[DefineEnvironment('defineEnvironmentWouldThrowsPDOException')]`, whose body is

```php
if (in_array($this->driver, ['pgsql', 'sqlsrv'])) {
    $this->expectException(PDOException::class);
}
```

Under `ferro-pgsql` the expectation is never armed, so the exception the test is *asking for*
propagates as an error. **Proven, not assumed**: the identical code under the `pgsql` alias turns
all six green, which also demonstrates that what the tier throws really is a `PDOException` subclass
reaching the assertion.

### Closed at C2b — the one engine gap C2 measured

`I64` could not bind PostgreSQL's `float8` or `numeric`: `testIncrement` (a PHP int into
`$table->float()`, i.e. `double precision`), `testWhereYear` and `testOrWhereYear`
(`extract(year from …) = ?`, which PostgreSQL types `numeric` since PG 14). Fixed in `PgInt` —
`numeric` with no value gate (arbitrary-precision, exact at every magnitude), `float8` gated on
exact representability and refused pre-send otherwise. SPEC §22.2 (an);
`docs/followups/2026-09-10-pg-bind-i64-into-float8-and-numeric.md` (RESOLVED). The predicted
+3 / +3 landed exactly.

## Two tier defects the first C2 run found and fixed (both in `php/laravel`)

1. **The execution paths skipped `prepareBindings()`.** Eloquent binds `Carbon` instances directly
   for datetime attributes, so `Model::create(['created_at' => $carbon])` reached the engine as a
   `DateTimeInterface`, was tagged canonical `TIMESTAMPTZ`, and was refused against the naive
   `timestamp` column `$table->timestamps()` creates. Unit tests with scalar bindings could not see
   it; the first real framework run failed on it immediately. (Errors 71 → 10.)
2. **The tier handed Illuminate the SPEC §9 value objects instead of PDO-shaped scalars.**
   `Builder::pluck($column, $key)` uses the key column's value as an array key —
   `TypeError: Cannot access offset of type Ferro\NaiveTimestamp on array` — and the same test then
   calls `substr()` on it. Fixed by passing `RawStringValuePolicy`, the same driver-native-string
   hand-off the Doctrine tier uses. Locked by `tests/Live/ScalarHydrationLiveTest`, mutation-proven
   (drop the argument and all three tests go red). (Errors 10 → 9.)

## Reproducing

```
docker compose -f testkit/docker-compose.yml up -d --wait pg
FERRO_LARAVEL_SVC=pg FERRO_LARAVEL_DSN='postgres://ferro:ferro@127.0.0.1:55432/laravel_tests' \
  bash testkit/laravel-suite.sh                                     # the ferro-pgsql column
FERRO_LARAVEL_DRIVER=pgsql FERRO_LARAVEL_SVC=pg FERRO_LARAVEL_DSN=... \
  bash testkit/laravel-suite.sh                                     # the alias column
```

The numbers above were produced on this container with system PostgreSQL 16.13 and
`FERRO_LARAVEL_SVC=psql` (a LOCAL `psql` running the identical `testkit/laravel/reset-pg.sql`, which
exists because a Docker daemon is not always available). The `laravel-suite` GitHub workflow runs
both columns twice each on a GH runner against the containerised backend; re-record from its logs
whenever the numbers change.
