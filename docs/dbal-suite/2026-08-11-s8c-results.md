### The wrapper the numbers cannot see

`Ferro\DBAL\Wrapper\FerroConnection` is documented as **required for correct SPEC §9.2 reporting**:
without it, an indeterminate write inside `Doctrine\DBAL\Connection::transactional()` — the canonical
Doctrine idiom — reaches the application as `Doctrine\DBAL\Exception\NoActiveTransaction` instead of
`Ferro\DBAL\IndeterminateWriteException` (the mechanism is in `3f581b5`). S8b's runner did not set
`db_wrapperClass`, so the recorded suite was measuring a configuration the driver's own docs call
wrong.

It was measured both ways, twice on each backend, before the runner was changed:

| | PG | MySQL | MariaDB |
|---|---|---|---|
| without `db_wrapperClass` | 3 errors / 7 failures | 2 / 9 | 2 / 9 |
| with `db_wrapperClass` | 3 errors / 7 failures | 2 / 9 | 2 / 9 |

**Every count is identical, and the ordered failure set is identical, on all three backends** — so
this changes nothing about the comparison with S8b. What it changes is what
`TransactionTest::testTransactionalFailureDuringCommit` actually reports:

```
without: exception of type "Doctrine\DBAL\Exception\NoActiveTransaction" … "There is no active transaction."
with:    exception of type "Ferro\DBAL\IndeterminateWriteException" … "connection lost during an
         in-flight non-readonly statement; the write may or may not have applied (§19.3 …)"
```

Equal counts, opposite meanings. A configuration change that silently alters WHAT IS BEING MEASURED
while leaving the result line untouched is the same false-green shape as the SQLite fallback, so it
gets the same treatment: `testkit/dbal/bootstrap.php` now REFUSES to run unless the connection is a
`FerroConnection`, next to the existing `getNativeConnection()` contact assertion. Deleting the
`db_wrapperClass` line from the runner makes the whole suite exit 1 with
`FERRO WRAPPER ASSERTION FAILED` rather than quietly reporting the same numbers.

Nothing had to be added to `reset-pg.sql` this time. S8b's first attempt drifted 71 → 72 because the
reset dropped a hand-written list of schemas; enumerating from `pg_namespace` fixed it, and that fix
still holds — the two runs are identical on a database the first run had already dirtied.

`Tests` counts everything PHPUnit collected including self-skipped tests; **passed** is
`tests − skipped − incomplete − errors − failures`. The large `skipped` count is unchanged and is
not a hidden failure: `TestUtil::isDriverOneOf()` answers false for every driver name (60 upstream
call sites; claiming `pdo_pgsql`/`pdo_mysql` would opt Ferro into PDO-specific expectations), so
every vendor-gated test takes its skip branch.

## The headline claims, proved end to end

The suite numbers say tests stopped failing. They do not say the promised capability works, so each
promise was exercised directly.

### 1. The stock `PostgreSQLSchemaManager` introspects a real table

`php/doctrine-dbal/tests/Live/TextFallbackLiveTest.php` (S8c task 1) covers columns, indexes and the
primary key, plus byte-identity with a real `pdo_pgsql` connection across the 20 expression classes
D-S8b-6 names. `php/doctrine-dbal/tests/Live/AdoptionAcceptanceLiveTest.php` (this task) adds
**FOREIGN KEYS**, through both `listTableForeignKeys()` and `introspectTable()`, on a composite
two-column FK with `ON DELETE CASCADE`.

A distinction worth recording rather than glossing, because it was measured: with the fallback
removed, `listTableForeignKeys()` **still passes** — its query selects only `pg_get_constraintdef`
and two booleans. It is `introspectTable()` that dies, because it also reads the indexes. So the
fallback did not make FK-reading work; it made the whole-table introspection that CARRIES the FKs
work — which is the call `doctrine/migrations` and `SchemaDiff` actually make.

### 2. `doctrine/migrations` really runs on PostgreSQL

A schema-manager test is a proxy for this claim, and the proxy is not the promise. So:
**`testkit/migrations-e2e.sh`** + **`testkit/migrations/`** — a real Composer project requiring
**`doctrine/migrations` 3.9.7** against the pinned `doctrine/dbal` 4.4.4, driving the real
`vendor/bin/doctrine-migrations` CLI, unpatched. The only Ferro-specific thing in the harness is
`driverClass` + `driverOptions` in `cli-config.php` — which is the config-only claim itself.

```
[ferro] migrations: fresh database ferro_migrations
[ferro] migrations: doctrine/migrations 3.9.7, doctrine/dbal 4.4.4
[ferro] migrations: driver=Ferro\DBAL\Driver platform=…\PostgreSQL120Platform server=PostgreSQL 17.10 …
 Generated new migration class to ".../generated/Version20260811082815.php"
[notice] finished in 16.5ms, used 6M memory, 1 migrations executed, 5 sql queries
 [OK] Successfully migrated to version: …Version20260811082815
[ferro] psql: 2 tables + index + FK + 1 recorded version — all present
  No changes detected in your mapping information.
[notice] Migrating down to 0 … 1 migrations executed, 3 sql queries
[ferro] psql: both tables gone, metadata table empty — rollback verified
[ferro] MIGRATIONS E2E: PASS (diff -> migrate -> empty diff -> rollback, all verified by psql)
```

Two properties of the harness are load-bearing and were each falsified before being trusted:

- **The second diff, not the first, is the proof.** With the fallback's mechanism removed, `diff`
  #1 and `migrate` both still PASS — an empty database has no index to read, so `pg_index.indkey` is
  never touched. Only `diff` #2, which introspects the tables that now exist, goes red
  (`column "indkey": PG type int2vector (OID 22) …`). A harness that stopped after "a migration was
  generated and ran" would have reported green with the fallback gone.
- **Every existence check is made by `psql` inside the container**, with Ferro out of the path.
  Replacing `migrations:migrate` with `migrations:migrate --dry-run` makes the CLI print
  `[OK] Successfully migrated to version: …` while doing nothing, and the oracle still fails the
  run. The same holds for the rollback half.

### 3. A spatial / custom-OID column ROUND TRIPS

D-S8b-6 states the mirror as a rule: *a value read as text must be writable back as text.* Reading
is half a claim, so `AdoptionAcceptanceLiveTest::testCustomOidValuesRoundTripThroughTheTextFallback`
closes the loop per type: seed a row server-side → Ferro READS it through the fallback → Ferro BINDS
THAT STRING BACK into a second row → **a direct `pdo_pgsql` connection reads the second row** and
must return identical bytes → and PostgreSQL is asked whether the two rows are equal.

13 types: **PostGIS `geometry`**, `hstore`, `ltree`, `citext`, a native ENUM, `interval`, `timetz`,
`inet`, `cidr`, `macaddr`, `int2vector`, `text[]`, `bit(4)`.

**PostGIS is real here, and its provenance is disclosed.** `postgis 3.6.4` was apt-installed into
the running `pg` container during S8c task 1; it is additive and is lost when the container is
recreated. The test therefore PROBES for the extension and PRINTS which branch it took —
`PostGIS: PRESENT — geometry ROUND TRIPPED (read as EWKB hex, bound back)` — so a fresh container
degrades loudly instead of silently dropping the spatial claim. The remaining custom-OID cases
(`hstore`, `ltree`, `citext`, the enum) are extension- and user-assigned OIDs too, so the class is
still covered without it.

## The bar, restated — and what of it is still unmeetable

SPEC §14 states the acceptance bar as *"DBAL 4 functional test suite green on PG + MySQL + SQLite;
ORM functional suite green on PG + MySQL"*. **That bar is still not met, and this pass does not
narrow it into one that is.**

1. **SQLite is impossible.** `engine/crates` has `pg` + `mysql` only (`AnyPool { Pg | Mysql }`).
   One third of the DBAL bar waits for `ferro-backend-sqlite`. Unchanged by this pass.
2. **The ORM functional suite has still never been run.** `doctrine/orm` is not a dependency of this
   repository and its harness has the same driver-injection problem. The ORM + PostgreSQL + IDENTITY
   incompatibility is documented (D-S8b-5, `docs/known-incompatibilities.md`) but *documented is not
   measured*. `doctrine/migrations` running is a real, user-visible capability; it is **not** the
   ORM suite and must not be reported as progress against that half of the bar.
3. **The upstream suite cannot select a third-party `driverClass`.** `TestUtil::getConnectionParams()`
   honours only `$params['driver']` and otherwise returns `['driver' => 'pdo_sqlite', 'memory' =>
   true]`. S8b reproduced the false green deliberately: with the contact assertion disarmed and
   upstream's `TestUtil` restored, `DataAccessTest` reported `OK (105 tests, 211 assertions)` against
   in-memory SQLite 3.45.1 with zero Ferro contact. `testkit/dbal/TestUtil.ferro.php` plus the
   bootstrap's contact assertion are what close it, and they are still the only thing that does.
4. **Even the stock drivers are not green on these containers** (S8b's measurement, not re-run here):
   `pdo_pgsql` over the whole `tests/` tree was `Tests 3913, Failures 1, Skipped 556, Incomplete 4`;
   `pdo_mysql` over `tests/Functional` was `Tests 1077, Errors 1057`.
5. **A subset, not the whole tree.** `testkit/dbal/allowlist.txt` selects 11 `tests/Functional` paths
   and records a reason for every exclusion.

**What this pass actually establishes:** on the curated subset, run through the real `DriverManager`
against a real backend with driver identity asserted, PostgreSQL is **364/374**, MySQL **374/385**,
MariaDB **373/384**, with every remaining non-passing test explained by a documented Ferro semantic
or a structural impossibility — and the stock PostgreSQL schema manager, schema diffing and
`doctrine/migrations` working end to end.

in as many words when `--no-reset` is used.
